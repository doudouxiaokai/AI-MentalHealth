## 1. 项目是什么

一个面向大学生的 AI 心理疏导 Web 应用，前后端分离。

- **用户端**：AI 心理对话（流式输出）、会话历史、情绪花园（对话后展示情绪分析）、情绪日记、心理知识库。
- **管理端**：数据看板（ECharts）、知识文章管理（富文本 CRUD）、咨询记录查阅、情绪日志查阅。

业务闭环的主链路是：**用户发一句话 → 后端建会话/存消息 → 调用大模型流式生成 → SSE 逐字推给前端 → 流结束后保存完整回复 → 前端拉取情绪分析结果**。

仓库结构：

```
AI-MentalHealth/
├── ai-spingboot/     # 后端，Maven 单模块，包名 org.example.aispingboot
└── ai-vue/           # 前端，Vue 3 + Vite
```

> 注意：后端目录名与包名是 `ai-spingboot` / `aispingboot`，`spring` 少写了一个 `r`。这是历史拼写，**面试口述时不要念错**，但代码里不需要改。

## 3. 运行时配置

`ai-spingboot/src/main/resources/application.yml`（完整语义）：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mental_health_assistant?useSSL=false&serverTimezone=UTC
    username: root
    password: 123456
  ai:
    openai:
      chat:
        options:
          model: deepseek-ai/DeepSeek-V3
          tool-calling:
            enabled: true
        completions-path: /v1/chat/completions
      api-key: you-key          # 硅基流动平台申请的真实 Key
      base-url: https://api.siliconflow.cn
server:
  port: 1236
jwt:
  secret: MySecretKeyForJWT2025!@#$%^&*()_+SecureKeyHere
  expiration: 86400000          # 24 小时，毫秒
  refresh-expiration: 604800000 # 7 天，毫秒（当前未使用）
  header: Authorization         # 配置存在但代码未读取
  token-prefix: "Bearer "       # 配置存在但代码未读取
```

**关键事实**

1. 后端端口 **1236**，不是 8080。
2. AI 走的是**硅基流动**的 OpenAI 兼容网关，模型名 `deepseek-ai/DeepSeek-V3`，`completions-path` 覆盖为 `/v1/chat/completions`。
3. JWT 的 `header` 与 `token-prefix` 配置**没有被任何代码使用**。`JwtAuthticationFilter` 实际读取的请求头名是 **`token`**（`JwtTokenUtil.extractTokenFromRequest` 中写死 `request.getHeader("token")`）。前端 `request.js` 与 `consultation.vue` 也都用 `token` 头。**这是一处配置与实现脱节**，面试若问「你的 Token 放在哪个请求头」应回答 `token`，不要按配置答 `Authorization`。
4. `refresh-expiration` 没有对应实现，项目**没有 refresh token 机制**。

## 5. 认证链路（JWT + Spring Security）

### 5.1 涉及类

- `SecurityConfig`：`@EnableWebSecurity` + `@EnableMethodSecurity`
- `JwtAuthticationFilter extends OncePerRequestFilter`
- `JwtTokenUtil`（静态方法）
- `JwtConfig`（配置绑定）
- `ResponseUtil`（过滤器内错误输出）

### 5.2 白名单

```java
private static final String[] PUBLIC_PATHS = {
    "/", "/api/test", "/api/user/login", "/api/user/add"
};
```

匹配用 Hutool 的 `AntPathMatcher`（`cn.hutool.core.text.AntPathMatcher`），逐条 `match`。`SecurityConfig.isPublicPATH(uri)` 是 `public static`，被过滤器复用。

### 5.3 安全策略

```java
http.csrf(AbstractHttpConfigurer::disable)
    .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
    .authorizeHttpRequests(auth -> auth
        .requestMatchers(PUBLIC_PATHS).permitAll()
        .anyRequest().authenticated())
    .addFilterBefore(jwtAuthticationFilter(), UsernamePasswordAuthenticationFilter.class);
```

要点：
- 关闭 CSRF（前后端分离 + Token 认证，无 Cookie 会话，CSRF 攻击面小）。
- `STATELESS`：不创建 HttpSession，每次请求都靠 Token 重新建立认证。
- 过滤器插在 `UsernamePasswordAuthenticationFilter` 之前。

### 5.4 Token 生成

`JwtTokenUtil.generateToken(Long userId, String username, Integer roleType)`：

```java
Algorithm algorithm = Algorithm.HMAC256(jwtConfig.getSecret());
Date expiration = new Date(System.currentTimeMillis() + jwtConfig.getExpiration());
JWT.create()
   .withClaim("userId", userId)
   .withClaim("username", username)
   .withClaim("roleType", roleType)
   .withExpiresAt(expiration)
   .withIssuedAt(new Date())
   .withIssuer("mental-health-assistant")
   .sign(algorithm);
```

- 算法 **HMAC256**（对称签名，密钥即 `jwt.secret`）。
- 三个自定义 Claim：`userId`、`username`、`roleType`（存的是 `userType`：1 普通用户 / 2 管理员）。
- 签发者常量 `ISSUER = "mental-health-assistant"`。
- 有效期 24 小时。
- **Payload 不加密**，只签名，所以 userId 等内容对客户端可见（前端也确实在用它判断跳转）。

### 5.5 过滤器执行流程

```
请求进入
  │
  ├─ shouldNotFilter? ── 命中 PUBLIC_PATHS → 直接放行（不解析 Token）
  │
  ├─ extractTokenFromRequest：读 header "token"，无值返回 null
  │
  ├─ 无 Token → clearSecurityContext() + ResponseUtil.writeError(ACCESS_UNAUTHORIZED) + return
  │            （HTTP 401，body 为 Result JSON）
  │
  ├─ validateToken：
  │     verifyToken  ─ HMAC256 验签 + withIssuer 校验 + 过期校验
  │                 ─ 失败抛 JWTVerificationException
  │     取 userId / username / roleType
  │
  ├─ userService.getUserById(userId) 回查数据库
  │     └─ 用户不存在 → 返回 null
  │
  ├─ 校验 user.getStatus() == UserStatus.NORMAL(1)
  │     ├─ 正常 → 构造 UsernamePasswordAuthenticationToken(username, null, [ROLE_1] 或 [ROLE_2])
  │     │          → SecurityContextHolder.setAuthentication(...)
  │     │          → request.setAttribute("jwtToken", token)
  │     └─ 禁用 → clearSecurityContext + writeError(TOKEN_ACCESS_FORBIDDEN) → 403
  │
  └─ chain.doFilter(request, response)
```

关键设计点：
1. **每次请求都回查数据库**校验用户状态，而不是只信 Token——这样管理员禁用账号能立刻生效，代价是每请求一次 `selectById`。
2. Token 解析结果除了放进 SecurityContext，还塞进 `request.setAttribute("jwtToken", token)`，供 Controller 用 `JwtTokenUtil.getCurrentToken()` 取原始 Token 再解析 userId（避免从 SecurityContext 拿主体字符串）。
3. 权限用 `ROLE_ + roleType` 字符串，如 `ROLE_1`、`ROLE_2`。项目里**没有使用** `@PreAuthorize`，管理端接口的权限实际只靠前端路由守卫，后端未做角色级拦截（这是缺陷，见第 11 节）。
4. `JwtTokenUtil` 是静态工具类，但需要 `JwtConfig`，所以实现 `ApplicationContextAware` 把 `ApplicationContext` 存进静态字段，再 `getBean(JwtConfig.class)`。这是「静态工具类取 Spring Bean」的常见妥协写法。

### 5.6 过滤器内如何返回错误

`ResponseUtil.writeError(response, ResultCode)`：

```java
int status = switch (resultCode) {
    case UNAUTHORIZED, ACCESS_UNAUTHORIZED, TOKEN_INVALID, TOKEN_EXPIRED, TOKEN_BLOCKED -> 401;
    case TOKEN_ACCESS_FORBIDDEN -> 403;
    default -> 400;
};
response.setStatus(status);
response.setContentType("application/json");
response.setCharacterEncoding("UTF-8");
// 手写 JSON 到 response.getWriter()
```

为什么需要它：过滤器在 DispatcherServlet 之前，`@RestControllerAdvice` 管不到这里，必须手工写响应体。这是面试可讲的一个细节。

### 5.7 登录流程

`UserController.login` → `UserService.login`：

```java
LambdaQueryWrapper<User> qw = new LambdaQueryWrapper<>();
qw.eq(User::getUsername, commandDTO.getUsername())
  .or()
  .eq(User::getEmail, commandDTO.getUsername());
User user = userMapper.selectOne(qw);
```

- 支持**用户名或邮箱**登录（同一个输入框）。
- `selectOne` 若匹配多条会抛异常，但 username / email 都有唯一性校验（注册时检查），理论不会。
- 密码校验：`new BCryptPasswordEncoder().matches(raw, stored)`；注册时 `encode`。
- 状态校验：`user.isActive()`（`status == 1`），禁用抛 `BusinessException("用户已被禁用，请联系管理员")`。
- 成功后 `UserConvert.entityToLoginResponse(token, userInfo)` 返回 `{ token, roleType, userInfo }`。
  - `roleType` 是 `userInfo.getUserType().toString()`，即字符串 `"1"` / `"2"`。
  - `userInfo` 里额外有 `displayName`（昵称优先）、`genderDisplayName`、`userTypeDisplayName`、`statusDisplayName`，都是实体方法算出来的。

### 5.8 注册流程

`UserService.register` 依次校验：
1. `password.equals(confirmPassword)`，否则「两次输入密码不一致」
2. 用户名已存在 → 「用户名已存在」
3. 邮箱已存在 → 「邮箱已存在」
4. `UserType.isValidCode(userType)` → 否则「无效的用户类型」
5. `passwordEncoder.encode(password)` 后入库，`status` 固定 `NORMAL(1)`，`createdAt/updatedAt` 手动赋值

DTO 层还有 Bean Validation 前置校验（见 5.9）。

## 6. AI 对话链路（核心）

### 6.1 ChatClient 与记忆的装配

`ChatClientConfig`：

```java
@Bean
public ChatMemory chatMemory() {
    return MessageWindowChatMemory.builder()
            .maxMessages(30)        // 只保留最近 30 条
            .build();
}

@Bean("open-ai")
public ChatClient openAiChatClient(OpenAiChatModel openAiChatModel) {
    return ChatClient.builder(openAiChatModel)
            .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory()).build())
            .defaultSystem("你是一个专业的心理疏导师，温和耐心，善于倾听，能够提供专业的心理支持和建议")
            .build();
}
```

要点：
1. `MessageWindowChatMemory` 是**内存实现**（`ConcurrentHashMap` 存 `conversationId -> List<Message>`），进程重启即丢，多实例不共享。
2. `maxMessages(30)` 是**滑动窗口**：超过 30 条时从最早的消息开始丢弃，保证 Prompt 不无限增长、控制 token 成本。
3. `MessageChatMemoryAdvisor` 是 Spring AI 的**对话记忆 Advisor**：请求前把该 `conversationId` 的历史消息自动拼进 Prompt，请求后把本轮消息写回 Memory。业务代码只需通过 `advisors(spec -> spec.param(ChatMemory.CONVERSATION_ID, id))` 指定会话标识。
4. `ChatClient` 的 bean 名是 `open-ai`，注入时用 `@Qualifier("open-ai")`。
5. `defaultSystem` 与 `PromptManage` 里的长提示词**同时存在**：`defaultSystem` 是简版，真正生效的是每次请求显式传入的 `SystemMessage`（长版），两者会叠加（Spring AI 会把 defaultSystem 和显式 SystemMessage 都带上），长版覆盖表达意图。

> `OpenAiChatModel` 由 `spring-ai-starter-model-openai` 自动装配，读取 `spring.ai.openai.*` 配置（api-key、base-url、model、completions-path）。所以「换模型」只需改 yml，不改代码——这是选 Spring AI 而不是手写 HTTP 的核心收益。

### 6.2 系统提示词（PromptManage）

`PSYCHOLOGICAL_SUPPORT_SYSTEM_PROMPT` 是一段固定中文长文本，结构为：

1. **角色设定**：专业、温暖、有同理心的 AI 心理健康助手，服务对象是**大学生**。
2. **角色特点**：温暖友善、专业不冷漠、善于倾听不急于建议、鼓励积极思考但不忽视负面情绪。
3. **对话原则（5 条）**：先共情 → 帮梳理情绪 → 给温和建议 → 必要时鼓励求助 → 强调用户价值。
4. **特殊注意（安全边界）**：
   - 检测到自杀倾向 → 优先表达关心，鼓励寻求专业帮助
   - 严重心理问题 → 建议联系学校心理咨询中心
   - 保持积极但现实，避免空洞安慰
5. **回复要求**：语言贴近大学生、长度适中、可适当用表情、结合校园场景。
6. **语言约束**：全程简体中文。

这段是**纯字符串常量**，没有做模板变量替换、没有版本管理、没有外部配置化。面试可讲「为什么把 Prompt 提到常量类」——避免散落在业务代码里，便于统一维护；也可坦承「更进一步应外置到配置中心或数据库，支持热更新与 A/B」。

### 6.3 创建会话

`POST /api/psychological-chat/session/start`

```java
public StructOutPut.StreamChatSession startSession(Long userId, ConsultationSessionCreateDTO dto) {
    ConsultationSession session = consultationSessionService.createSession(userId, dto);
    consultationMessageService.saveUserMessage(session.getId(), dto.getInitialMessage(), null);

    String sessionId = "session_" + session.getId();
    return new StructOutPut.StreamChatSession(
        sessionId, userId, dto.getInitialMessage(),
        System.currentTimeMillis(),
        System.currentTimeMillis() + 86400000L,  // 24h
        1, "ACTIVE");
}
```

`createSession` 内部：
- 先 `userMapper.selectById(userId)` 确认用户存在，不存在返回 `null`（**注意：会 NPE**，见缺陷清单）。
- 标题为空时兜底：`"宁渡AI助手 - " + DateUtil.format(now, "MM-dd HH:mm")`。
- `startedAt = LocalDateTime.now()`，`insert` 后回填自增 ID。

**会话 ID 的两种形态**（关键概念，面试常问）：
- **数据库主键**：`Long id`，如 `12`。
- **对外会话标识**：`"session_12"`，前端持有的是这个。
- **模型记忆标识**：`"conversation_session_12"`，在 `streamPsychologicalChat` 里由 `"conversation_" + sessionId` 拼成。

三者是**刻意解耦**的：业务会话可持久化、可回看；模型记忆是运行时概念，与数据库无关；前缀让解析可逆（`extractSessionId` 用 `substring("session_".length())` 反解）。

返回结构 `record StreamChatSession`：
```java
(String sessionId, Long userHash, String initialMessage,
 Long startTime, Long expiryTime, Integer messageCount, String status)
```
`userHash` 实际塞的是 `userId`（命名不准确）；`messageCount` 固定 1（刚存了初始消息）；`status` 固定 `"ACTIVE"`；`expiryTime` 是当前时间 + 24 小时。

### 6.4 流式对话（最关键的一段）

`POST /api/psychological-chat/stream`，`produces = MediaType.TEXT_EVENT_STREAM_VALUE`

`PsychologicalSupportService.streamPsychologicalChat(sessionId, userMessage)` 返回 `Flux<String>`：

```java
return Flux.create(sink -> {
    Long dbSessionId = extractSessionId(sessionId);          // "session_12" -> 12
    if (dbSessionId == null) { sink.error(...); return; }

    // ① 幂等判定：是否为「初始消息」
    boolean isInitialMessage = false;
    Integer count = messageService.getMessageCountBySessionId(dbSessionId);
    if (count == 1) {
        ConsultationMessageResponseDTO last = messageService.getLastMessageBySessionId(dbSessionId);
        if (last != null && last.getSenderType() == 1
                && userMessage.equals(last.getContent())) {
            isInitialMessage = true;
        }
    }
    if (!isInitialMessage) {
        messageService.saveUserMessage(dbSessionId, userMessage, null);
    }

    // ② 记忆与 Prompt
    String conversationId = "conversation_" + sessionId;
    chatMemory.add(conversationId, List.of(new UserMessage(userMessage)));
    Prompt prompt = new Prompt(List.of(
        new SystemMessage(PromptManage.PSYCHOLOGICAL_SUPPORT_SYSTEM_PROMPT)));

    // ③ 调用模型 + 流式桥接
    StringBuilder full = new StringBuilder();
    chatClient.prompt(prompt)
        .user(userMessage)
        .advisors(spec -> spec.param(ChatMemory.CONVERSATION_ID, conversationId))
        .stream()
        .content()                       // Flux<String>，按 token 片段产出
        .doOnNext(f -> { full.append(f); sink.next(f); })
        .doOnComplete(() -> {
            messageService.saveAimessage(dbSessionId, full.toString(), "openai");
            chatMemory.add(conversationId, List.of(new AssistantMessage(full.toString())));
            sink.complete();
        })
        .doOnError(sink::error)
        .subscribe();
});
```

**逐点解释（面试重点）**

① **为什么需要幂等判定**
时序是：前端先调 `session/start`（此时后端已经 `saveUserMessage(初始消息)`），紧接着调 `stream` 并**原样再传一遍**初始消息。如果不判定，同一句话会入库两次，历史记录里出现重复。判定条件用「消息总数 == 1 && 最后一条是用户发的 && 内容完全一致」，三个条件同时满足才算「这条已经存过了」，从而跳过二次入库。

> 局限：只覆盖「会话第一条消息」这一种场景。若用户在 `stream` 接口重复提交同一句话（比如网络重试），仍会重复入库——没有做基于 requestId 的幂等键。

② **为什么用 `Flux.create` 而不是 `Flux.fromIterable`**
因为数据源是异步推送的（模型逐 token 回调），`Flux.create` 拿到 `FluxSink`，可以在任意时机的回调里 `next/complete/error`，把「推模式」的回调桥接成「拉模式」的流。这是 Reactive Streams 里适配异步回调的标准手法。

③ **`sink` 的三个动作**
- `sink.next(fragment)`：向下游发一个片段
- `sink.complete()`：正常结束
- `sink.error(e)`：异常结束（必须显式调用，否则 `Flux.create` 内部的异常不会自动传播到 HTTP 层，前端会一直挂着）

④ **`doOnComplete` 里落库**
流式过程中只累积不写库，全部结束后一次性 `saveAimessage` 存完整回复。好处是避免每个 token 写一次库；代价是**如果客户端中途断开、或进程崩溃，这条 AI 回复不会入库**（`doOnComplete` 不触发）。这是真实缺陷，改进方向是 `doFinally` 或定期 flush，或先落库占位再增量更新。

⑤ **`delayElements(Duration.ofMillis(50))` 在哪里**
在 Controller 里，不是 Service 里：

```java
return service.streamPsychologicalChat(...)
    .map(f -> ServerSentEvent.<String>builder().event("message")
            .data(JSONUtil.toJsonStr(Result.ok(Map.of("content", f, "type", "normal"))))
            .build())
    .concatWith(Flux.just(ServerSentEvent.<String>builder().event("done").data("{}").build()))
    .delayElements(Duration.ofMillis(50));
```

`delayElements` 作用于**整个流**，包括每个 `message` 和最后的 `done`。效果是把上游产出节奏压到最快 20 个/秒，人为制造「打字机」观感，避免一次性刷出一大段。副作用是整体响应变慢（100 个片段要多花 5 秒），并且 `delayElements` 默认使用 `Schedulers.parallel()`，会占用调度线程。

⑥ **为什么 Advisor 和手动 `chatMemory.add` 同时存在（潜在重复）**
`MessageChatMemoryAdvisor` 在请求前会读取历史、请求后写入本轮消息。而代码里又手动 `add` 了 `UserMessage` 和 `AssistantMessage`。理论上同一轮消息会被写两次，导致上下文重复膨胀。这是一个**设计冗余**，正确做法是二选一：要么只依赖 Advisor（删掉手动 add），要么手动管理记忆、不用 Advisor。面试若被追问「你的多轮对话怎么保证上下文不重复」，可以坦诚说明这是待优化点，并给出正确方案。

⑦ **`subscribe()` 的必要性**
`Flux.create` 的 lambda 在**被订阅时**才执行；Controller 返回的 Flux 由 Spring MVC 订阅，所以外层会被订阅。但内部 `chatClient...subscribe()` 是**二次订阅**，它启动对模型的调用并通过 `sink` 往外推。这种「外层 Flux 被订阅 → 内部再订阅另一个流」的写法能工作，但不是最优雅的桥接方式；更规范的是 `Flux.create` 里返回 `chatClient...subscribe(sink::next, sink::error, sink::complete)`，或用 `Flux.using` / `concatMap` 组合，避免双订阅带来的背压丢失。

### 6.5 SSE 报文格式

每条 `message` 事件的 `data` 是一个 `Result` JSON：

```
event: message
data: {"code":"200","msg":"操作成功","data":{"content":"你好","type":"normal"}}

event: message
data: {"code":"200","msg":"操作成功","data":{"content":"，我在","type":"normal"}}

event: done
data: {}
```

- `content` 是**片段**，不是完整句，前端负责累加。
- `type` 固定 `"normal"`（预留了扩展位，如 `"emotion"`，但未使用）。
- `done` 事件是 Controller 用 `concatWith` 追加的，标志流正常结束。
- 认证失败时（`userId == null`）返回单个 `event: error`，`data` 是 `code=401` 的 Result JSON。

### 6.6 前端如何消费 SSE

`consultation.vue` 用 `@microsoft/fetch-event-source` 的 `fetchEventSource`：

```js
const ctrl = new AbortController()
fetchEventSource('/api/psychological-chat/stream', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Token': localStorage.getItem('token'),   // 注意：浏览器会规范化 header 名，服务端 getHeader("token") 大小写不敏感
    'Accept': 'text/event-stream'
  },
  body: JSON.stringify({ sessionId, userMessage }),
  signal: ctrl.signal,
  onopen: (res) => {
    if (res.headers.get('Content-Type') !== 'text/event-stream') { /* 提示非流式 */ }
  },
  onmessage: (event) => {
    if (event.event === 'done') { isAiTyping.value = false; ctrl.abort(); loadSessionEmotion(...); return }
    const payload = JSON.parse(event.data)
    if (String(payload.code) === '200' && payload.data?.content) {
      aiMessage.content += payload.data.content     // 累加到同一条消息对象
    }
  },
  onerror: (err) => { handleError(err); throw err },
  onclose: () => { loadSessionEmotion(...) }
})
```

**为什么不用原生 `EventSource`**（必答）：
1. 原生 `EventSource` 只支持 **GET**，无法携带请求体，而这里要 POST 传 `sessionId` + `userMessage`。
2. 原生 `EventSource` **不能自定义请求头**，无法带 `token`。
3. 原生只支持自动重连，无法精细控制中止。
`fetch-event-source` 基于 `fetch` + `ReadableStream`，支持 POST、自定义头、`AbortController` 中止，并内置了 SSE 解析与断线重连策略。

**前端如何保证「同一条气泡逐字增长」**：先 push 一个空的 `aiMessage` 对象，`onmessage` 里持续 `aiMessage.content += fragment`，Vue 的响应式让同一 DOM 节点重渲染，视觉上就是打字机。

**中止**：`new AbortController()` + `signal`，`done` 或手动停止时 `ctrl.abort()`。注意 abort 只是断开浏览器侧连接，后端 Flux 不会感知（没有 `doOnCancel` 清理），模型调用会继续跑完并写库。

### 7.2 表设计要点（面试可讲）

1. **会话与消息分表**：一对多。会话表只存元信息（标题、时间、最后情绪），消息表存流水。好处是列表查询只扫会话表，不必聚合消息；坏处是列表页要显示「最后一条消息预览」时需要额外查询（当前后端未实现该接口，前端字段 `lastMessageContent` 无数据来源）。
2. **逻辑外键，无物理外键**：`user_id`、`session_id` 都只是普通列 + 索引（代码里没有 `FOREIGN KEY`），避免分库分表和高并发写入时的外键开销，一致性由业务层保证。
3. **状态用数字而非字符串**：`user_type`、`status`、`sender_type` 都是 TINYINT，配枚举类 `UserType` / `UserStatus` 做语义映射，节省空间且便于索引。
4. **命名规范**：数据库 snake_case，Java camelCase，靠 MyBatis-Plus 的驼峰映射 + 显式 `@TableField("user_id")` 双重保证。
5. **索引**：代码层未建索引（建表 SQL 在 README 中补了 `idx_user`、`idx_session`）。按 `user_id` 查会话列表、按 `session_id` 查消息是最高频查询，必须有索引。

### 7.3 MyBatis-Plus 用法

- 三个 Mapper 都是空接口 `extends BaseMapper<T>`，**没有 XML、没有自定义 SQL**。
- 条件构造全部用 `LambdaQueryWrapper`，如：
  ```java
  new LambdaQueryWrapper<ConsultationMessage>()
      .eq(ConsultationMessage::getSessionId, sessionId)
      .orderByDesc(ConsultationMessage::getCreatedAt)
      .last("limit 1");
  ```
  `LambdaQueryWrapper` 用方法引用取列名，避免手写字符串字段名，编译期可校验。
- `.last("limit 1")` 是**字符串拼接 SQL 尾部**，属于 MP 提供的逃生舱；此处参数是常量，无注入风险，但坏习惯要说明。
- **没有注册分页插件**：`PaginationInnerInterceptor` 未配置，所以 `selectPage` 不可用。前端调用的 `/psychological-chat/sessions?pageNum=&pageSize=` 这类分页接口在后端也不存在。
- `IdType.AUTO`：依赖数据库自增，插入后 MP 回填 `id`（`createSession` 拿 `session.getId()` 拼 `"session_" + id` 就依赖这个回填）。

## 8. 统一响应与异常

### 8.1 Result 结构

```json
{ "code": "200", "msg": "操作成功", "data": { } }
```

`code` 是 **String**，不是 int。`Result` 提供 `ok()` / `ok(data)` / `error()` / `error(code, msg, data)` 四个静态工厂。

`ResultCode` 枚举关键项：

| 枚举 | code | msg |
| --- | --- | --- |
| SUCCESS | `"200"` | 操作成功 |
| ERROR | `"-1"` | 操作失败 |
| UNAUTHORIZED | `"401"` | 暂未登录或token已经过期 |
| PARAM_ERROR | `"400"` | 参数错误 |
| SYSTEM_ERROR | `"500"` | 系统错误 |
| TOKEN_INVALID / TOKEN_EXPIRED / TOKEN_BLOCKED | 都是 `"A0230"` | 分别为无效/过期/黑名单 |
| TOKEN_ACCESS_FORBIDDEN | `"A0231"` | token已被禁止访问 |
| ACCESS_UNAUTHORIZED | `"A0301"` | 访问未授权 |

> 注意：三个 Token 错误码共用 `"A0230"`，前端无法区分「过期」和「无效」。且前端 `request.js` 判断的失效码是 `"-1"`，与 `A0230/A0301` 对不上——真实影响是：Token 过期时，后端返回 HTTP 401 + `code=A0301`，axios 走 **error 分支**（因为 401 是 4xx），而 error 分支只是 `Promise.reject`，**不会清 token 跳登录**。这是一个真实的前后端契约不一致。

### 8.2 GlobalExceptionHandler

`@RestControllerAdvice`，只处理两类：

1. `MethodArgumentNotValidException`（`@Valid` 校验失败）→ 拼接所有字段错误消息，`code=400`。
2. `BusinessException` → `Result.error(e.getCode(), e.getMessage(), e.getData())`。

**没有兜底 `Exception` 处理器**，所以未捕获异常（NPE、SQL 异常、`JWTVerificationException` 在 Controller 里抛出的）会走 Spring 默认错误处理，返回 `{"timestamp":..., "status":500, "error":"Internal Server Error", "path":...}`，结构与 `Result` 不一致。前端拿到这种响应会解析失败。

### 8.3 BusinessException 的语义

```java
public class BusinessException extends RuntimeException {
    private final String code = "BUSINESS_ERROR";
    private final String message;
    private final Object data = null;
    public BusinessException(String message) { super(message); this.message = message; }
}
```

只有单参构造，`code` 永远是 `"BUSINESS_ERROR"`。业务层抛出的所有「用户不存在」「密码错误」「邮箱已存在」都走这一个码。前端 `request.js` 只认 `"200"` 和 `"-1"`，**不认 `"BUSINESS_ERROR"`**，所以登录失败时前端拿到的既不是成功也不是失效，而是原样返回 response 对象——`login.vue` 里 `data.token` 会是 `undefined`，走 `if (!data.token) return console.error('登录失败')` 分支。表现是「点登录没反应，控制台有日志」，这是可指出的体验缺陷。

### 9.2 路由与三套布局

| 布局 | 前缀 | 子路由 |
| --- | --- | --- |

### 9.3 路由守卫

```js
router.beforeEach((to, from, next) => {
  const token = localStorage.getItem('token')
  if (token) {
    const userInfo = JSON.parse(localStorage.getItem('userInfo'))
    if (userInfo.userType == 2) {                 // 管理员
      to.path.startsWith('/back') ? next() : next('/back/dashboard')
    } else if (userInfo.userType == 1) {          // 普通用户
      (to.path.startsWith('/back') || to.path.startsWith('/auth')) ? next('/') : next()
    }
  } else {
    to.path.startsWith('/back') ? next('/auth/login') : next()
  }
})
```

要点：
- 双端隔离：管理员只能待在后端，普通用户不能进 `/back` 和 `/auth`。
- **纯前端拦截，不是安全边界**：直接 curl 后端接口不受此限制，真正的权限必须后端做（当前后端没做角色校验，见缺陷）。
- 隐患：`token` 存在但 `userInfo` 被清掉时，`JSON.parse(null)` 返回 `null`，`null.userType` 抛错，守卫中断，页面白屏。健壮写法应先判空。
- 隐患：`userType` 既不是 1 也不是 2 时，三个分支都不进，`next()` 永远不会被调用，导航挂起。

### 9.4 Axios 封装

`utils/request.js`：

```js
const service = axios.create({ baseURL: '/api', timeout: 5000 })

service.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers['token'] = token
  return config
})

service.interceptors.response.use(response => {
  const { data, config } = response
  if (data.code === '200') return data.data        // 直接剥壳，业务层拿到的就是 data
  else {
    if (data.code === '-1') {
      // 清 token + userInfo + 跳 /auth/login（登录接口除外）
    }
  }
  return response
}, error => Promise.reject(error))
```

- `baseURL: '/api'` 配合 Vite 代理转发到后端，避免开发期跨域。
- 请求拦截统一注入 `token` 头，业务代码不用关心鉴权。
- 响应拦截**剥壳**：`return data.data`，所以 `login()` 的 then 里拿到的是 `{ token, roleType, userInfo }`，而不是完整 `Result`。
- `timeout: 5000` 对普通接口够用，但**不适用于 SSE**（SSE 用 `fetchEventSource` 直连 `/api/...`，不经过 axios，因此没有 5 秒超时问题）。
- 缺陷：只处理 `"200"` 和 `"-1"`，`"BUSINESS_ERROR"`、`"400"` 等都不处理也不 reject，调用方容易拿到非预期结构（见 8.3）。

### 9.6 Markdown 渲染

`MarkdownRenderer.vue` 是**手写正则渲染器**，没有用 `marked` / `markdown-it`：

1. 先转义 `<` `>` 防 XSS；
2. 依次替换代码块、行内代码、粗体、斜体、标题（h1-h3）、链接、无序/有序列表、引用、分割线；
3. `v-html` 输出。

为什么手写：AI 回复的 Markdown 子集很有限，手写零依赖、体积小、可控。风险：正则渲染对嵌套结构（列表套列表、表格、代码块内含反引号）支持不全，且转义顺序稍有不慎仍有 XSS 风险。生产级应换 `marked` + `DOMPurify`。

### 9.7 富文本与上传

`RichTextEditor.vue` 封装 `@wangeditor/editor-for-vue`：

- `editorCreated` 时把编辑器实例回传父组件，编辑态用 `editor.setHtml(content)` 回填。
- `onChange` 把 `editor.getHtml()` 抛给父组件写入 `formData.content`。
- 图片上传走 `uploadFile(file, businessInfo)`：`FormData` 里带 `file`、`businessType=ARTICLE`、`businessId`、`businessField=cover`。
- 封面地址拼接：`fileBaseUrl + fileRes.filePath`，`fileBaseUrl` 来自 `src/config/index.js`，值是 `http://159.75.169.224:1235`（**硬编码公网地址，与本地后端不一致**）。
- 大小校验 `file.size / 1014 / 1014 < 5`，除数应为 1024，实际阈值约 5.14MB（小 bug）。

## 11. 已知缺陷与改进方向（面试加分素材）

### 11.1 配置与端口

- `vite.config.js` 的代理 `target: 'http://159.75.169.224:1235'`，而后端端口是 **1236**，IP 还是公网地址。本地联调必须改成 `http://localhost:1236`，否则所有请求打到那台服务器。
- `config/index.js` 的 `fileBaseUrl` 同样是 `http://159.75.169.224:1235`，且硬编码在源码里，没有走环境变量（Vite 应用 `import.meta.env.VITE_*`）。

### 11.2 认证

- `jwt.header` / `jwt.token-prefix` 配置项**未被读取**，实际用 `token` 头；配置形同虚设。
- **没有 refresh token**：`refresh-expiration` 配置存在但无代码使用，24 小时到期必须重新登录。
- **没有登出服务端失效机制**：无 Redis/黑名单，Token 签发后在有效期内始终可用。前端 `handleLogout` 调 `/api/user/logout`（后端不存在），404 导致 `.then` 不执行，**实际点退出登录没反应**——只能手动清 localStorage。
- **后端无角色级鉴权**：`ROLE_1` / `ROLE_2` 塞进了 SecurityContext，但没有 `@PreAuthorize` 或路径级 `hasRole` 配置，普通用户直接请求管理端接口（若将来实现）不会被拦。
- 每请求回查数据库，高并发下是额外压力，可加短 TTL 缓存（Caffeine/Redis）。

### 11.3 AI 与流式

- `MessageWindowChatMemory` 是**进程内内存**，重启丢失、多实例不共享。生产应换 `RedisChatMemory` 或自实现持久化记忆（表里已有 `last_emotion_analysis`，但没有消息级记忆表）。
- **记忆双写**：Advisor 自动写 + 手动 `chatMemory.add`，可能重复。
- **流中断丢数据**：`doOnComplete` 才落库，客户端 abort 或服务崩溃则 AI 回复不入库。
- **客户端断开无感知**：没有 `doOnCancel` / `sink.onDispose` 处理，abort 后模型仍跑完、仍写库、仍占 token 费用。
- `delayElements(50ms)` 是人为限速，既拖慢整体，又占用 parallel 调度器；更好做法是前端做渲染节流，后端不干预。
- 无**超时控制**：模型长时间不返回时，SSE 连接会一直挂（Tomcat 的 async timeout 默认 30s，但未显式配置，行为不确定）。
- 无**内容安全兜底**：只有 Prompt 里的软约束，没有敏感词过滤、没有危机干预的强制转介逻辑（如检测到自杀关键词必须弹出热线）。
- 无**token 计量与成本控制**：30 条窗口是唯一约束，没有按用户限流/配额。

### 11.4 前端

- `register.vue`：`register(formData).then(({ data }) => ...)` 解构错误。响应拦截器已 `return data.data`，所以这里 `data` 是 `undefined`，`if (!data)` 恒为真 → **注册失败也提示「注册成功」并跳登录页**。正确写法是 `.then(() => 成功).catch(...)`，或后端业务错误时让拦截器 reject。
- `ArticleDialog.handleSubmit`：`if (valid) { loading.value = true }` 之后，提交逻辑写在 `if` **外面**，校验不通过也会提交。
- `beforeUpload` 的 `1014` 应为 `1024`。
- `consultation.vue` 里 `formatMessageContent` 用 `replace(/\n/g,'<br>')` 拼 HTML，与 `MarkdownRenderer` 的 `v-html` 并存，存在 XSS 面。
- 会话列表的 `lastMessageContent`、`messageCount`、`durationMinutes` 字段无后端来源，页面显示为空/0。
- 无 loading / 骨架屏 / 错误重试；SSE 失败只 toast 一次。
- Element Plus 全量引入，未按需。
- 无 ESLint / Prettier / TypeScript，无单元测试。

### 11.5 工程化

- 无全局跨域配置（开发靠 Vite proxy，生产需 Nginx 同源转发或加 `CorsConfiguration`）。
- 无接口文档（可加 springdoc-openapi）。
- 无 Docker / CI，部署靠手工。
- 配置文件明文放数据库密码与 API Key，应改环境变量 + 配置中心。
- `System.out.println` 调试语句残留多处（`JwtAuthticationFilter`、`UserService`、`ConsultationSessionService`）。
- 包名拼写 `aispingboot`，目录 `ai-spingboot`，对外叙述易读错。
- 无分页插件，导致列表接口无法用 MP 分页。
- 无 `@Transactional`：注册（查重 + 插入）、会话创建（查用户 + 插会话 + 插消息）都是多步写操作，缺少事务边界，异常时可能留下半截数据。
