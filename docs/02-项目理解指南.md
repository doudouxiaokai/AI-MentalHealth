# 心理健康 AI 咨询平台 · 项目理解指南

> 这份是给你自己看的。不追求覆盖所有代码细节，目标是把项目「讲明白」——面试时能用大白话说清它是怎么运转的，以及每个设计为什么这么定。

---

## 一、一句话说清它是什么

一个大学生用的 AI 心理疏导网站。用户打开聊天框说「我最近很焦虑」，AI 不是一次性甩出一大段回复，而是像打字一样一个字一个字往外蹦；聊完之后，左侧会显示这次对话的情绪分析（偏负面/风险等级/给你的建议）。

除此之外还有情绪日记、心理知识库两个辅助模块，以及一个管理员后台（看数据看板、管文章、查咨询记录）。

技术上就两套东西：Spring Boot 提供登录鉴权和 AI 流式对话，Vue 3 提供界面。

## 二、先看懂两条链路，其他都是枝叶

### 链路 A：登录（理解认证）

```
输入用户名密码
  → POST /api/user/login
  → 后端用「用户名 或 邮箱」查 user 表
  → BCrypt 比对密码（数据库存的是密文）
  → 检查 status 是不是 1（正常）
  → 签发 JWT（里面塞 userId / username / roleType，24 小时过期，HMAC256 签名）
  → 返回 { token, userInfo }
  → 前端把 token 和 userInfo 塞进 localStorage
  → 之后每次请求，Axios 拦截器自动在 header 里加 token
```

之后每个请求进后端，都会先过一道 `JwtAuthticationFilter`：

```
读 header 里的 token
  → 没有 → 直接返回 401 JSON（不进 Controller）
  → 有 → HMAC256 验签 + 校验 issuer + 校验是否过期
       → 从 token 里拿 userId
       → 去数据库查这个用户
       → 用户被禁用了？→ 403
       → 正常 → 把用户身份放进 SecurityContext，放行
```

**为什么要每次查库？** 因为 JWT 一旦签发，服务端无法撤回。如果只在登录时查一次状态，管理员把某人禁用后，他拿着旧 token 还能用 24 小时。每请求查一次，禁用能立刻生效。代价是每个请求多一次 `selectById`。

**为什么用 JWT 不用 Session？** 前后端分离、要水平扩展时，Session 需要粘性会话或共享存储；JWT 自带状态，服务端不用存。代价是无法主动失效，所以才有上面「查库」这个补丁。

### 链路 B：聊天（理解流式，这是项目的技术核心）

这里有个容易懵的点：**建会话和发消息是两个接口**。

```
① 用户点「新建会话」后发第一句话
   → POST /session/start  { initialMessage: "我最近很焦虑" }
   → 后端：建一条 session 记录 + 把这句话存进 message 表
   → 返回 sessionId = "session_12"

② 前端立刻调
   → POST /stream  { sessionId: "session_12", userMessage: "我最近很焦虑" }
   → 注意：同一句话又传了一遍！
```

**为什么不一件事一次做完？** 因为流式接口是 SSE 长连接，不适合再做「建资源」这种一次性动作；分开后，会话创建是普通的 JSON 请求，失败可重试，流式只负责「往这个会话里说话」。

**那同一句话不就存两次了吗？** 所以 `stream` 里有个幂等判定：

```
if (这个会话只有 1 条消息
    && 最后一条是用户发的
    && 内容和这次传的一模一样) {
    说明这句话在 start 时已经存过了 → 跳过，不再插入
}
```

三个条件必须同时成立。这是项目里少数「考虑过边界」的地方，面试值得主动讲。

**流式是怎么实现的**：

```
Service 返回 Flux<String>
  → 调 chatClient.stream().content()，模型每吐一个片段就回调一次
  → 用 Flux.create 拿到 sink（一个「出水口」）
  → 每来一个片段：拼到 StringBuilder 里，同时 sink.next(片段)
  → 全部结束：把完整回复一次性写入 message 表，sink.complete()
  → Controller 把每个片段包装成 SSE 事件（event: message, data: {content:"..."}）
  → 最后补一个 event: done
  → 每个事件 delayElements(50ms)，制造打字机节奏
```

**前端怎么接**：用 `fetch-event-source` 而不是浏览器原生 `EventSource`。原因是原生只支持 GET、不能带自定义请求头，而这里必须 POST 传参 + 带 token。收到一个片段就 `aiMessage.content += 片段`，Vue 响应式让同一个气泡不断变长。

**多轮对话的上下文怎么保持**：`MessageChatMemoryAdvisor` + `MessageWindowChatMemory(30)`。每次请求，Advisor 自动把该会话最近 30 条历史拼进 Prompt；模型因此「记得」前面说过什么。30 是滑动窗口上限，超了丢最早的，控制 token 成本。

## 三、七个必须能讲清的机制

### 1. 会话 ID 有三层，是故意分开的

| 形态 | 例子 | 谁在用 |
| --- | --- | --- |
| 数据库主键 | `12` | 后端落库 |
| 对外会话 ID | `session_12` | 前端持有、传给后端 |
| 模型记忆 ID | `conversation_session_12` | Spring AI 的 ChatMemory |

**为什么搞这么麻烦**：数据库主键是数字，直接暴露给前端不好看也不好扩展；加前缀后，后端能反解（`substring` 掉前缀），同时把「业务会话」和「模型记忆」两个概念彻底分开——记忆是运行时的东西，将来换成 Redis 存储也不影响业务表。

### 2. 系统提示词单独放在一个常量类

`PromptManage.PSYCHOLOGICAL_SUPPORT_SYSTEM_PROMPT`，内容分六块：角色设定 → 角色特点 → 五条对话原则 → 安全边界（自杀倾向要先共情并引导求助、严重问题建议找学校心理咨询中心）→ 回复要求（贴近大学生、长度适中）→ 语言约束（全程中文）。

**为什么单独提出来**：不散落在业务代码里，改 Prompt 不用动逻辑；也方便将来外置到配置或数据库做热更新。

**面试可能追问「怎么防止 AI 说错话」**：目前只有 Prompt 软约束，没有硬性敏感词过滤和强制转介，这是欠缺——诚实承认，并说改进方向（关键词拦截 + 危机话术模板 + 热线弹窗）。

### 3. 九张表，但只有三张接上了代码

数据库里实际有 **9 张表**（完整结构见 `sql/schema.sql`），但 Java 只映射了 3 张——这个「设计多、实现少」的差距，是你讲这张架构图时最有信息量的地方。

**已接上代码的三张**（对话主链路）：

- `user`：账号，密码 BCrypt 密文（`$2a$10$` 前缀，cost=10），`user_type` 区分普通用户(1)/管理员(2)，`status` 区分正常(1)/禁用(0)。username / email / phone 三个都是唯一索引。
- `consultation_session`：会话的「壳」，存标题、开始时间、**最后一次情绪分析结果**。
- `consultation_message`：消息流水，`sender_type` 区分谁说的（1 用户 / 2 AI）。

**只有表、没有代码的六张**（前端页面已经写好了）：

- `emotion_diary`：情绪日记。`mood_score` 1-10、`sleep_quality` 1-5、`stress_level` 1-5，还有一段 `ai_emotion_analysis`。**`UNIQUE(user_id, diary_date)` 保证一个人一天只能写一篇。**
- `ai_analysis_task`：AI 分析任务队列。这张表最有讲头——`status` 有 PENDING/PROCESSING/COMPLETED/FAILED 四个状态，`task_type` 有 AUTO/MANUAL/ADMIN/BATCH 四种触发方式，`priority` 1-4，还有 `retry_count` / `max_retry_count` 重试机制、`error_message`、`started_at` / `completed_at`。配上 10 个索引（其中三个联合索引分别对应「按优先级取任务」「按时间取任务」「按类型批量取任务」）。
- `knowledge_category` + `knowledge_article` + `user_favorite`：知识库三件套。文章主键是 **UUID 而不是自增**，正文是 LONGTEXT 存富文本 HTML，收藏是独立的关联表且有唯一约束防重复。
- `sys_file_info`：通用文件表。用 `business_type + business_id + business_field` 三个字段定位「这个文件属于哪个业务对象的哪个字段」，还带 `is_temp` + `expire_time` 支持临时文件自动过期。头像和文章封面都走这一张表。

**这张图说明什么**：`ai_analysis_task` 的存在证明——情绪分析在设计上是**异步**做的：用户写完日记，先插一条任务记录，后台 worker 再慢慢算，算完回写日记表的 `ai_emotion_analysis`。而不是让用户请求卡在那里等模型。这是个挺专业的设计，虽然 worker 代码不在当前仓库里。

**两个必须讲对的细节**：

1. **表里有物理外键，而且是级联删除**。`consultation_message.session_id → consultation_session.id ON DELETE CASCADE`，删会话自动删消息；删用户会级联删掉他的会话、消息、日记、任务、收藏。但知识文章对分类和作者是 **RESTRICT**——有文章的分类/作者不能删。这个区别体现的是「从属数据可以跟着主体消失，知识资产不行」。
   > ⚠️ 别再按「互联网公司都不用外键」去答。这个项目用了，你就讲清为什么用它（数据量小、要强一致、省应用层代码），再讲代价（级联删除不可控、分库后失效、写入有检查开销）。能讲出取舍比背教条得分高。
2. **`last_emotion_analysis` 是 JSON 类型**，里面存的结构和前端 `currentEmotion` 对象一模一样：`primaryEmotion`、`emotionScore`、`isNegative`、`riskLevel`、`riskDescription`、`suggestion`、`improvementSuggestions`、`keywords`、`icon`、`label`、`timestamp`。也就是说**数据契约和前端渲染都齐了，只差后端生成这一段**。

**为什么会话和消息分表**：会话列表页只查会话表就够了，不用扫几万条消息；消息按 `(session_id, created_at)` 联合索引查，还顺便按时间排好序。典型的一对多拆分。

### 4. 统一响应体 + 两处异常出口

所有接口返回 `{ code, msg, data }`，`code` 是**字符串**（`"200"`、`"-1"`、`"BUSINESS_ERROR"`）。

异常有两个出口，这点值得讲：

- **Controller 层**：`@RestControllerAdvice` 捕获参数校验失败（`MethodArgumentNotValidException`）和业务异常（`BusinessException`）。
- **过滤器层**：`JwtAuthticationFilter` 在 DispatcherServlet 之前执行，`@RestControllerAdvice` 管不到，所以必须用 `ResponseUtil` 手动往 `response.getWriter()` 写 JSON。

**这是「过滤器 vs 拦截器 vs 全局异常」三者边界的一个真实例子**，能讲清楚说明你真理解请求处理链。

### 5. 前端路由守卫做双端隔离

管理员（`userType=2`）只能待 `/back/**`，普通用户（1）不能进 `/back` 和 `/auth`。守卫读 localStorage 里的 `userInfo` 判断。

**必须强调**：这只是**体验层拦截，不是安全边界**。直接 curl 后端接口完全绕过。真正的权限必须后端做——而项目后端目前没做角色校验（`ROLE_1`/`ROLE_2` 塞进了 SecurityContext 但没用 `@PreAuthorize`），这是可承认的短板。

### 6. Axios 拦截器做了三件事

1. 请求前自动加 `token` 头（业务代码不用管鉴权）。
2. 响应 `code === "200"` 时**剥壳**，直接返回 `data.data`，所以调用方 `login().then(res => res.token)` 就能拿到。
3. `code === "-1"` 时清 token 并跳登录页。

`baseURL: '/api'` + Vite 代理，开发期不用处理跨域。

**顺带一个真实 bug**（如果面试官问「你项目有什么问题」可以拿来说）：后端业务异常返回的 code 是 `"BUSINESS_ERROR"`，前端只认 `"200"` 和 `"-1"`，所以登录失败时前端既不成功也不跳转，表现为「点登录没反应」。根因是前后端错误码契约没对齐。

### 7. 前端只用 Pinia 存了一个折叠状态

`stores/admin.js` 里只有一个 `isCollapse`（侧边栏展开/收起）。其他状态（登录态、会话列表、消息）全是组件内 `ref` + localStorage。

**别吹成「用 Pinia 做了状态管理」**。诚实说法：项目里 Pinia 只承担了 UI 状态，登录态走 localStorage，跨组件共享需求少。如果追问「为什么不全用 Pinia」，答：当前规模没必要，Pinia 状态刷新即丢，登录态需要持久化，所以 localStorage 更直接。

## 四、面试官会从哪里切进来

按经验，看简历上这个项目，提问路径通常是这四条：

**路径 1（最常见）：先让你讲项目**
→ 你用「一句话定位 + 两条链路」讲完
→ 他抓一个点深挖，大概率是「流式怎么做的」

**路径 2：盯着 AI 部分**
→ 为什么用 Spring AI 不直接调 HTTP
→ 多轮对话上下文怎么保持
→ 30 条窗口满了怎么办
→ 重启后记忆还在吗（答：不在，内存实现，这是缺陷）

**路径 3：盯着认证**
→ 为什么用 JWT 不用 Session
→ token 放哪、过期怎么办、能不能主动失效
→ 过滤器里怎么返回 JSON 错误
→ 前端路由守卫能防住直接调接口吗（不能，必须后端做）

**路径 4：盯着数据库**
→ 为什么分两张表
→ 会话 ID 为什么加前缀
→ 有没有用事务（没有，这是缺陷）
→ 索引怎么建

**最容易被问倒的三个点，提前准备**：
1. 你不就一个 `/stream` 接口吗，会话列表接口在哪？→ 坦白：前端写了，后端未实现。
2. 用户中途关掉页面，AI 回复还存得下来吗？→ 存不下来，`doOnComplete` 不触发。
3. 多台服务器部署，对话记忆还对吗？→ 不对，内存实现，要换 Redis。

## 五、项目短板怎么答（别硬撑）

面试官问「这个项目有什么不足」，不要说「没什么不足」，也不要自我贬低。用这个结构：**承认现象 → 说清原因 → 给出方案**。

| 短板 | 一句话答法 |
| --- | --- |
| 记忆是内存的 | 「用的是 `MessageWindowChatMemory`，进程内 Map，重启即丢、多实例不共享。生产会换 Redis 存储或落一张消息记忆表。」 |
| 流中断丢回复 | 「只在 `doOnComplete` 落库，客户端 abort 就不会写。改成先插入占位记录、流结束再更新内容，或 `doFinally` 兜底。」 |
| 后端接口不全 | 「主链路（认证 + 流式对话）是完整实现的。数据库其实设计了 9 张表，知识库、情绪日记、异步分析任务、文件管理这几块的表结构都建好了，但对应的 Java 实体和接口还没提交，前端页面倒是写完了。」 |
| 没有事务 | 「注册的查重 + 插入、建会话的查用户 + 插会话 + 插消息，都是多步写操作，没加 `@Transactional`，极端情况会有半截数据。」 |
| 没有主动登出 | 「JWT 无状态，没有黑名单机制；而且登出接口后端没实现，前端点了其实没反应，只能手清 localStorage。」 |
| 前端没做权限 | 「路由守卫只是体验层，后端也没有 `@PreAuthorize` 做角色校验，这是要补的。」 |

**反面教材**：不要说「用了 Redis 做缓存」「用了 AOP 做日志」「用了消息队列削峰」——项目里一个都没有，一追就崩。

## 六、必须记住的数字

| 数字 | 含义 |
| --- | --- |
| **1236** | 后端端口（不是 8080） |
| **30** | 对话记忆窗口条数 |
| **50ms** | SSE 每个事件的延迟 |
| **24 小时** | JWT 有效期（86400000 毫秒） |
| **2000** | 单条消息最大字符数 |
| **9 / 3** | 数据库 9 张表，Java 只映射了 3 张 |
| **1 / 2** | 用户类型（普通/管理员）、消息发送方（用户/AI）、状态（禁用/正常，0/1） |
| **DeepSeek-V3** | 模型名 `deepseek-ai/DeepSeek-V3`，走硅基流动 |
| **session_ / conversation_** | 两层 ID 前缀 |

## 八、最后一句心态提醒

这个项目的定位是**实习简历项目**，面试官不会期待它有高并发、分布式、灰度发布。他们真正想确认三件事：

1. **这条流式链路是你自己写的还是抄的**——能说清 `sink` 为什么存在，就赢了。
2. **你有没有边界意识**——幂等判定、`doOnComplete` 丢数据、内存记忆，这些你能自己指出，比藏起来强得多。
3. **你知不知道正确做法**——承认缺陷的同时给出 Redis、事务、`@PreAuthorize` 这些方案，就说明你不是只会跑通。

把「我知道它哪里不完善，也知道该怎么改」讲出来，比假装完美更容易过。
