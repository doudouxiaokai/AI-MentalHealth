## A. 项目概述与背景

### Q1. 简单介绍一下你的这个项目 ⭐

**参考答案**
这是一个面向大学生的心理健康 AI 咨询平台，前后端分离。核心功能是 AI 心理疏导对话——用户说一句话，后端调用大模型，通过 SSE 把回复一个字一个字推给前端，做出打字机效果；对话结束后会做情绪分析，在侧栏显示情绪倾向和风险等级。另外还有情绪日记、心理知识库两个辅助模块，以及一个管理员后台，能看数据看板、管理文章、查咨询记录。

技术上后端是 Spring Boot 3.5 + MyBatis-Plus + MySQL + Spring Security + JWT，AI 部分用 Spring AI 对接 DeepSeek-V3；前端是 Vue 3 + Vite + Element Plus，图表用 ECharts。

**可能追问**
- 「流式是怎么实现的？」→ 直接进 Q28，这是最容易被追的点。
- 「后端接口都写完了吗？」→ 不要硬说全写完，见 Q6。

### Q2. 这个项目你觉得最难的地方在哪 ⭐⭐

**参考答案**
最难的是流式对话这条链路，因为它是「异步回调」和「同步 HTTP 响应」之间的转换。

模型是一段一段吐字的，是推模式；但 HTTP 请求要有明确的响应体，是拉模式。中间要用 Reactor 的 `Flux.create` 拿一个 `FluxSink` 当桥梁：模型每吐一个片段，我就 `sink.next(fragment)` 往下游推；全部结束再 `sink.complete()`；出错必须显式 `sink.error()`，否则前端会一直挂着等。

第二个难点是细节的边界：同一句话会不会存两次、用户中途关页面回复会不会丢、记忆窗口满了怎么办。这些不是「跑通」的问题，是「跑对」的问题。

**可能追问**
- 「为什么不用 WebSocket？」→ Q12。
- 「sink.error 不调用会怎样？」→ 前端连接一直不关闭，浏览器一直转圈，直到超时。

### Q7. 如果让你重做一遍，你会怎么改 ⭐⭐⭐

**参考答案**
三个层面。

架构上，把 AI 调用抽成独立的 `AiChatService` 接口，实现类可以换 DeepSeek、通义、本地模型，业务层不依赖具体厂商。

可靠性上，流式回复改成「先落库占位、再增量更新」——现在是等流结束才写库，用户中途关页面这条回复就没了。同时加 `doOnCancel`，客户端断开就取消模型调用，省 token。

工程上，补 `@Transactional`（注册、建会话都是多步写）、补后端角色鉴权（现在只有前端路由守卫）、把配置里的密钥换成环境变量。

**可能追问**
- 「为什么先落库占位？」→ 这样即使流中断，至少有一条带部分内容的记录，比彻底丢失好；也便于做「重新生成」。

## B. 技术选型

### Q8. 为什么用 Spring Boot 3 而不是 2.x ⭐⭐

**参考答案**
主要是两个原因。一是 JDK 基线，Spring Boot 3 要求 Java 17，我用的是 17，能用 record、switch 表达式、文本块这些新特性——项目里 `StructOutPut` 就是用 record 写的。二是 Spring AI 的 1.0 版本要求 Boot 3，我要用 Spring AI 就只能上 3。

另外 Boot 3 全面迁到 Jakarta EE（`javax.*` 变 `jakarta.*`），比如校验注解是 `jakarta.validation.constraints.NotBlank`，这个迁移在当时是个坑。

**可能追问**
- 「Boot 3 和 2 还有什么区别？」→ 原生镜像支持（GraalVM）、Micrometer 可观测性增强、Problem Details 支持。知道就说，不知道就说不了解细节。

### Q9. 为什么用 MyBatis-Plus 不用 JPA ⭐⭐

**参考答案**
两个考虑。一是 SQL 可控，心理项目里查询条件会变（按用户查会话、按会话查消息、按时间倒序取最后一条），MyBatis-Plus 的 `LambdaQueryWrapper` 写起来直观，而且用方法引用取列名（`ConsultationMessage::getSessionId`），编译期能校验，不怕字段改名。

二是团队习惯，国内大部分公司用 MyBatis 系，实习出去更通用。JPA 的优点是简单 CRUD 不用写 SQL、跨数据库好，但复杂查询要么写 JPQL 要么掉回原生 SQL，优势不明显。

**可能追问**
- 「MyBatis-Plus 的 LambdaQueryWrapper 原理？」→ 通过 `SerializedLambda` 解析方法引用，反推出属性名，再转成数据库列名。
- 「用了分页插件吗？」→ **没有**，这是缺陷，`PaginationInnerInterceptor` 没注册，所以 `selectPage` 用不了。

### Q10. 为什么用 JWT 不用 Session ⭐⭐

**参考答案**
因为前后端分离。Session 依赖 Cookie + 服务端存储，多实例部署时要做会话共享（Redis）或者粘性会话，麻烦；JWT 把状态放在客户端，服务端只验签，天然支持水平扩展。

第二个原因是跨端：将来要做小程序或 App，Cookie 机制不好带，Token 放请求头更通用。

代价是 JWT 无法主动失效——签发后在有效期内一直能用。我的补丁是**每次请求都回查数据库校验用户状态**，这样管理员禁用账号能立刻生效。

**可能追问**
- 「那 JWT 比 Session 好吗？」→ 不是，是场景不同。内部管理系统、单体应用用 Session 更简单；对外 API、多端、微服务用 JWT 更合适。
- 「JWT 能不能主动失效？」→ 能，加黑名单（Redis 存 jti，TTL 设为剩余有效期），或者用短有效期 + refresh token。项目里都没做。

### Q11. 为什么用 Spring AI，不自己用 HttpClient 调 ⭐⭐

**参考答案**
三个收益。

一是模型可替换。Spring AI 的 `OpenAiChatModel` 读的是 `spring.ai.openai.*` 配置，改 `base-url` 和 `model` 就能从 OpenAI 换成硅基流动的 DeepSeek，代码一行不动。我实际就是这么接的 DeepSeek——用 OpenAI 协议兼容层，`base-url` 指到 `https://api.siliconflow.cn`。

二是流式、记忆、Advisor 这些是现成的。手写要自己处理 SSE 解析、上下文拼接、异常重试；Spring AI 用 `chatClient.prompt().stream().content()` 一行拿到 `Flux<String>`，`MessageChatMemoryAdvisor` 自动管上下文。

三是生态，将来接 RAG、Function Calling、向量库都是同一套 API。

**可能追问**
- 「Spring AI 有什么坑？」→ 1.0.0-SNAPSHOT 版本还在演进，API 有变动；文档相对少；出问题要读源码。项目里就遇到过 Advisor 和手动 `chatMemory.add` 重复写上下文的问题。

### Q12. 为什么用 SSE 不用 WebSocket ⭐⭐⭐（高频重点）

**参考答案**
因为这个场景是**单向**的：用户发一句，服务端流式回一段。不需要客户端和服务端随时互推，WebSocket 的全双工能力用不上，反而带来额外成本——要维护连接状态、要做心跳、要处理重连、Nginx 要额外配置 upgrade。

SSE 是基于 HTTP 的，天然穿过代理和网关，浏览器断线会自动重连（我用 `fetch-event-source` 是为了支持 POST 和自定义头，它内部也做了重连），实现成本低得多。

一句话：**单向流用 SSE，双向实时（聊天室、协同编辑、游戏）才用 WebSocket。**

**可能追问**
- 「SSE 有什么缺点？」→ 浏览器原生 `EventSource` 只能 GET、不能带自定义头（所以我用了 fetch 版）；HTTP/1.1 下同域并发连接数有限制（6 个）；不适合二进制。
- 「那你的项目算即时通讯吗？」→ 不算，是一问一答的流式响应，本质是「慢一点的 HTTP 响应」。

## C. 认证与安全

### Q15. JWT 是什么，由哪几部分组成 ⭐

**参考答案**
JSON Web Token，三段用 `.` 分隔：Header、Payload、Signature。

Header 说明算法（我用 HMAC256），Payload 放 claim（我放了 `userId`、`username`、`roleType`，还有标准的 `exp` 过期时间、`iat` 签发时间、`iss` 签发者），Signature 是用密钥对前两段做的签名。

关键点：**Payload 只是 Base64 编码，不是加密**，任何人都能解开看内容，所以不能放密码这类敏感信息。它保证的是「没被篡改」，不是「看不见」。

**可能追问**
- 「那为什么还安全？」→ 因为改任何一位，签名就对不上，服务端验签会失败。

---

### Q16. token 存在哪里，为什么 ⭐⭐

**参考答案**
前端存在 `localStorage`，每次请求由 Axios 拦截器加到请求头 `token` 里。

选 localStorage 而不是 Cookie，是因为不想让请求自动带凭证——Cookie 会自动随请求发送，容易有 CSRF 问题；放 localStorage 手动加头，配合后端关掉 CSRF 是自洽的。

但 localStorage 的缺点是**能被 JS 读到**，一旦有 XSS 就能偷走 token。更安全的方案是 HttpOnly Cookie + CSRF Token，但那套对前后端分离不友好。

**可能追问**
- 「那你项目有 XSS 风险吗？」→ 有面。AI 回复是用 `v-html` 渲染的，虽然手写的 Markdown 渲染器先转义了 `<` `>`，但正则渲染器本身不够严谨，生产应该上 `DOMPurify`。

### Q17. token 过期了怎么处理 ⭐⭐

**参考答案**
后端在验签时会校验 `exp`，过期直接抛 `JWTVerificationException`，过滤器捕获后返回 HTTP 401 + JSON 错误体。

前端理想情况是收到 401 就清 token 跳登录页。但**项目这里有个真实的不一致**：`request.js` 里判断的失效码是 `"-1"`，而后端 401 走的是 axios 的 error 分支（4xx 不会进 then），error 分支只做了 `Promise.reject`，并不会清 token 跳转。所以实际表现是接口报错但页面没跳登录。

正确做法是在 error 分支里判断 `error.response.status === 401` 再统一处理。

**可能追问**
- 「为什么不做 refresh token？」→ 配置里留了 `refresh-expiration` 但没实现，这是待补的。

---

### Q18. 用户被管理员禁用后，还能用旧 token 访问吗 ⭐⭐

**参考答案**
不能。因为过滤器验签通过后，会拿 token 里的 `userId` 去数据库查用户，校验 `status == 1`（正常）。如果被禁用（0），直接返回 403，并清掉 SecurityContext。

这是 JWT「无法主动失效」的补丁。代价是每个请求多一次 `selectById`，高并发下可以加一层短 TTL 缓存。

**可能追问**
- 「为什么不把状态也放进 token？」→ 放进去也没用，token 签发后状态就固定了，用户被禁用时旧 token 里的状态还是「正常」。必须查库或查缓存。

---

### Q19. 为什么过滤器里要查数据库，不是解析完 token 就够了吗 ⭐⭐

**参考答案**
两个原因。一是状态实时性，就是上一题说的禁用要立刻生效。二是防止「token 里的用户已经不存在」——比如账号被删了，但 token 还没过期，光验签会放行一个不存在的用户。

**可能追问**
- 「性能怎么优化？」→ Caffeine 本地缓存（几十秒 TTL）或 Redis，把用户状态缓存起来；或者用「token 版本号」机制，用户状态变更时版本 +1，token 里带旧版本号就失效。

### Q20. 过滤器、拦截器、AOP 有什么区别 ⭐⭐⭐

**参考答案**
按执行顺序：**Filter → Interceptor → AOP → Controller**。

- **Filter** 是 Servlet 规范的，在 `DispatcherServlet` 之前，能拿到原始 `HttpServletRequest/Response`，但拿不到「哪个 Controller 的哪个方法」。我的 JWT 校验就放在这里（`OncePerRequestFilter`）。
- **Interceptor** 是 Spring MVC 的，在 `DispatcherServlet` 之后、Controller 之前，能拿到 `HandlerMethod`，适合做权限注解、日志。
- **AOP** 是方法级的，能拿到方法参数和返回值，适合做事务、缓存、埋点。

**选型逻辑**：需要在进入 Spring MVC 之前拦（比如认证、编码）用 Filter；需要知道目标方法用 Interceptor；需要包裹方法执行用 AOP。

**可能追问**
- 「为什么 JWT 用 Filter 不用 Interceptor？」→ 因为要在最外层拦，未认证的请求连 DispatcherServlet 都不该进；而且 Filter 能直接写 response 短路。

---

### Q21. 为什么过滤器里不能靠全局异常处理返回错误 ⭐⭐⭐

**参考答案**
因为 `@RestControllerAdvice` 是 Spring MVC 的机制，它依赖 `DispatcherServlet` 的异常解析链。而 Filter 在 `DispatcherServlet` **之前**执行，那时异常解析器还没接管，抛出去也不会被 advice 捕获，只会变成容器级的 500 页面。

所以我在过滤器里用 `ResponseUtil.writeError()` 直接往 `response.getWriter()` 写 JSON，并且按错误类型设置 HTTP 状态码（401/403）。

这也是个容易踩的坑：**很多人以为加了全局异常处理就万事大吉，结果过滤器里的异常照样吐 HTML。**

**可能追问**
- 「那过滤器的异常怎么统一？」→ 就是手工封装一个工具类，保证输出格式和 `Result` 一致。项目里 `ResponseUtil` 干的就是这事。

### Q22. BCrypt 为什么比 MD5 安全 ⭐⭐

**参考答案**
三点。

一是**自带盐**，每次加密都随机生成 salt 并存在结果里，同样的密码两次加密结果不同，彩虹表失效。MD5 不加盐的话，同一个密码哈希永远一样。

二是**慢**，BCrypt 有可调的计算轮数（cost），故意设计得慢，暴力破解成本高。MD5 太快了，GPU 每秒能算几十亿次。

三是**专为密码设计**，MD5 是通用摘要算法，本来就不该用于存密码。

我项目里注册时 `passwordEncoder.encode(raw)`，登录时 `matches(raw, stored)`——`matches` 会自动从密文里取出盐再比对，不用自己管盐。

**可能追问**
- 「BCrypt 密文为什么每次不一样还能比对成功？」→ 因为盐存在密文字符串里（`$2a$10$...` 格式），`matches` 解析出来复用。

### Q23. 你的接口怎么防止越权访问别人的数据 ⭐⭐⭐

**参考答案**
坦白说，这块**目前做得不完整**，是个要补的点。

现状是：`/api/user/current` 是从 token 里取 `userId` 再查，这个没问题；但会话相关的查询接口（前端已调、后端待实现）如果只按 `sessionId` 查，没有校验「这个会话是不是当前用户的」，就会有越权——改一下 URL 里的 id 就能看别人的咨询记录。

正确做法是在 Service 层加归属校验：`WHERE id = ? AND user_id = ?`，用当前登录用户的 id 兜底，而不是只按主键查。心理数据属于高敏感信息，这个必须做。

**可能追问**
- 「怎么统一做？」→ 可以在 MyBatis-Plus 上加租户/数据权限插件，或者写一个 `@DataScope` 注解 + AOP 自动拼 `user_id` 条件。
- ⚠️ 这题**主动承认 + 给出方案**，比硬说「我做了」好。面试官很可能就是顺着这个点看你的安全意识。

### Q24. 前端路由守卫算安全措施吗 ⭐⭐

**参考答案**
不算，只是体验层。

路由守卫读 localStorage 里的 `userInfo.userType`，管理员进 `/back`、普通用户进前台，防止用户看到不该看的页面。但这是**浏览器里的 JS**，用户完全可以手动改 localStorage，或者直接 curl 后端接口，守卫一点用没有。

真正的权限必须在后端做：接口级校验角色。项目里我把 `ROLE_1` / `ROLE_2` 放进了 SecurityContext，但**没有用 `@PreAuthorize` 或路径级 `hasRole` 去校验**，所以后端目前是不设防的。这是明确的短板。

**可能追问**
- 「怎么补？」→ 管理端接口加 `@PreAuthorize("hasRole('2')")`，或在 `SecurityConfig` 里对 `/api/admin/**` 配 `hasRole("2")`；同时前端守卫保留，做体验优化。

### Q25. 密码能明文存吗，加盐是干什么的 ⭐

**参考答案**
绝对不能明文存。一旦库被拖，所有用户密码直接泄露，而且用户往往多站复用密码，影响会扩散。

加盐是给每个密码拼一段随机字符串再哈希，目的是让**相同的密码产生不同的哈希**，这样攻击者不能用预先算好的彩虹表批量反查，也不能看出「哪些用户用了同一个密码」。

**可能追问**
- 「盐要不要保密？」→ 不需要，盐可以跟哈希一起存，它的作用不是保密而是「唯一化」。

### Q26. 如果 token 被盗了怎么办 ⭐⭐⭐

**参考答案**
这是 JWT 的固有弱点。理论上没救——token 是无状态凭证，谁拿到谁就能用，服务端无法区分「本人」和「小偷」。

实际能做的：
1. **缩短有效期**，减少被盗后的可利用窗口（我现在是 24 小时，偏长，可以缩到 2 小时 + refresh token）。
2. **黑名单**，发现异常时把该 token 的 `jti` 塞进 Redis，TTL 设为剩余有效期，验签时查一次。
3. **绑定设备指纹**（IP / UA 哈希）写进 claim，不一致就拒绝——但会影响移动网络切换场景。
4. **敏感操作二次验证**。

心理数据敏感，我认为应该做「短有效期 + refresh + 黑名单」这套。

**可能追问**
- 「黑名单放 Redis，Redis 挂了怎么办？」→ 降级为「放行但记日志」，或本地缓存兜底，可用性优先。

### Q27. 你是怎么调用大模型的 ⭐

**参考答案**
用 Spring AI 的 `ChatClient`。配置在 `ChatClientConfig` 里定义一个 bean：

```java
ChatClient.builder(openAiChatModel)
    .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory()).build())
    .defaultSystem("你是一个专业的心理疏导师...")
    .build();
```

业务里注入这个 bean（名字叫 `open-ai`），然后：

```java
chatClient.prompt(prompt)
    .user(userMessage)
    .advisors(spec -> spec.param(ChatMemory.CONVERSATION_ID, conversationId))
    .stream()
    .content();
```

`OpenAiChatModel` 是 starter 自动装配的，读 `application.yml` 里的 `spring.ai.openai.*`——我配的是硅基流动的 `base-url` + `deepseek-ai/DeepSeek-V3` 模型名，走 OpenAI 兼容协议。

**可能追问**
- 「`.stream()` 和 `.call()` 区别？」→ `call()` 阻塞等完整结果，返回 `ChatResponse`；`stream()` 返回 `Flux<String>`，逐片段推送。

### Q28. 流式输出的原理是什么 ⭐⭐（必答）

**参考答案**
整条链路分四段：

**第一段，模型侧**：调 `chatClient.stream()` 后，Spring AI 用 `WebClient` 发请求，服务端以 SSE 格式持续返回 `data: {...}` 片段，Spring AI 把它解析成 `Flux<String>`，每个元素是一个 token 片段。

**第二段，后端桥接**：我用 `Flux.create(sink -> ...)` 把「回调推送」转成「Flux 流」。模型每来一个片段，`doOnNext` 里既拼进 `StringBuilder`，又 `sink.next(fragment)` 往下游发。全部结束 `doOnComplete` 里落库 + `sink.complete()`。

**第三段，HTTP 层**：Controller 返回 `Flux<ServerSentEvent<String>>`，`produces = text/event-stream`。Spring MVC 识别到响应式返回值 + SSE，就把每个元素序列化成 `event: message\ndata: {...}\n\n` 写进响应流，并且不关闭连接，直到 Flux 结束。

**第四段，浏览器侧**：前端用 `fetch-event-source` 拿到 `ReadableStream`，按 SSE 协议切分事件，每收到一个就 `aiMessage.content += fragment`，Vue 响应式触发重渲染，视觉上就是打字机。

**可能追问**
- 「后端是一次性返回还是多次返回？」→ 一次 HTTP 响应，但响应体是分块传输（chunked），服务端边算边写。
- 「中间有代理会缓冲吗？」→ 会。Nginx 默认 `proxy_buffering on` 会把流攒起来，必须关掉并加 `X-Accel-Buffering: no`，否则流式效果消失。这是上线必踩的坑。

### Q29. Flux.create 和 Flux.just 有什么区别 ⭐⭐⭐

**参考答案**
`Flux.just(a, b, c)` 是**已知的、有限的**元素，创建时就把数据定好了，同步发射。

`Flux.create` 是**未知的、异步的**，它给你一个 `FluxSink`，你可以在未来任意时刻调用 `next/complete/error`，什么时候有数据什么时候推。它解决的是「把一个回调式 API 适配成响应式流」的问题。

我的场景必须用 `create`，因为模型的片段是在网络回调里陆续到达的，创建 Flux 的那一刻我一个片段都没有。

**可能追问**
- 「还有别的创建方式吗？」→ `Flux.fromIterable`（集合）、`Flux.interval`（定时）、`Flux.from`（包装已有 Publisher）、`Sinks.many()`（更现代的写法）。
- 「Sinks 和 Flux.create 哪个好？」→ Sinks 是更新的 API，支持多播和背压策略配置；`create` 更老但够用。项目里用的是 `create`。

### Q30. sink 是什么，为什么需要它 ⭐⭐⭐

**参考答案**
`sink` 是 `FluxSink`，可以理解成这个流的「出水口」或者说「遥控器」。它有三个核心方法：

- `sink.next(x)`：发射一个元素
- `sink.complete()`：正常结束
- `sink.error(e)`：异常结束

为什么需要它：我的数据源是「模型的回调」，不是「一个现成的集合」。我不能 return 一个集合，只能拿到一个可以随时塞数据的句柄，`sink` 就是这个句柄。

**关键一点**：异常必须显式 `sink.error()`。如果 `Flux.create` 的 lambda 里抛异常而没调 `sink.error`，这个异常不会自动传播到 HTTP 层，下游永远等不到结束信号——前端就一直转圈。

**可能追问**
- 「sink.next 之后还能 next 吗？」→ 能，只要没 complete/error。
- 「背压怎么办？」→ `Flux.create` 默认忽略背压（`FluxSink.OverflowStrategy.IGNORE`），我的场景数据量小，可以接受；严谨做法是选 `BUFFER` 或 `DROP` 并处理 `onRequest`。

### Q31. 为什么要 delayElements(50ms) ⭐⭐

**参考答案**
为了观感。模型有时候返回很快，片段会「唰」一下全出来，反而看不出流式的效果；每 50ms 放一个，大约每秒 20 个片段，正好是舒服的打字节奏。

但我要说清楚这是**权宜之计**，它有两个副作用：

一是拖慢整体——如果一条回复有 200 个片段，光延迟就 10 秒；二是 `delayElements` 默认跑在 `Schedulers.parallel()` 上，占用调度线程。

更好的做法是**后端不限速，前端做渲染节流**（比如用 `requestAnimationFrame` 合并更新），或者按字符数而不是片段数控制节奏。

**可能追问**
- 「delayElements 会影响顺序吗？」→ 不会，它保证顺序，只是每个元素延后固定时间。
- 「为什么不用 Thread.sleep？」→ 会阻塞 Tomcat 线程，直接打死并发能力。响应式里绝不能用阻塞。

### Q32. SSE 的报文长什么样 ⭐

**参考答案**
纯文本，事件之间用空行分隔，每行是 `字段: 值`：

```
event: message
data: {"code":"200","msg":"操作成功","data":{"content":"你好","type":"normal"}}

event: message
data: {"code":"200","msg":"操作成功","data":{"content":"，我在","type":"normal"}}

event: done
data: {}
```

四个字段：`event`（事件名，前端按名字区分）、`data`（数据，只能是字符串）、`id`（可选，用于断线重连续传）、`retry`（可选，重连间隔）。

我的约定是：`message` 事件带片段，`done` 事件标志结束，认证失败时发 `error` 事件。

**可能追问**
- 「data 能放 JSON 对象吗？」→ 不能直接放，必须是字符串，所以我在后端用 `JSONUtil.toJsonStr()` 序列化了。
- 「为什么每条都包一层 Result？」→ 复用统一响应结构，前端解析逻辑一致，也能在流里传错误码。

### Q33. 前端为什么不用原生 EventSource ⭐⭐

**参考答案**
三个硬伤：

1. **只支持 GET**，不能带请求体。我需要 POST 传 `sessionId` 和 `userMessage`，长文本放 URL 不现实。
2. **不能自定义请求头**，没法带 `token`。虽然可以把 token 放 query 参数，但会出现在日志和浏览器历史里，不安全。
3. **不能精细控制**，原生只提供 `close()`，重连策略是固定的。

`@microsoft/fetch-event-source` 基于 `fetch` + `ReadableStream` 自己解析 SSE，支持 POST、自定义头、`AbortController` 中止，还内置了带退避的重连。代价是要自己处理一些边界（比如 `onopen` 里校验 Content-Type）。

**可能追问**
- 「那它的重连有什么坑？」→ 默认会在 `onerror` 后重连，如果业务错误也重连会死循环，需要在 `onerror` 里 `throw` 出去阻止重连。我项目里就是这么做的。

### Q34. 多轮对话的上下文是怎么保持的 ⭐⭐

**参考答案**
靠 Spring AI 的 `ChatMemory` + `MessageChatMemoryAdvisor`。

`ChatMemory` 我用的是 `MessageWindowChatMemory`，本质是一个 `Map<conversationId, List<Message>>`，存每个会话的历史消息。`maxMessages(30)` 限制只保留最近 30 条。

`MessageChatMemoryAdvisor` 是自动挡：请求前，它按 `conversationId` 取出历史，拼到 Prompt 前面；请求后，它把这一轮的用户消息和 AI 回复写回 Memory。业务代码只需要在调用时指定会话标识：

```java
.advisors(spec -> spec.param(ChatMemory.CONVERSATION_ID, conversationId))
```

我的 `conversationId` 是 `"conversation_" + sessionId`，跟数据库会话一一对应。

**可能追问**
- 「30 条是怎么算的？」→ 用户消息 + AI 消息各算一条，一轮问答占 2 条，所以实际记住约 15 轮。
- 「超了会怎样？」→ 从最早的开始丢，模型「忘记」最早的内容。这也是为什么长对话后面会显得「失忆」。

### Q35. 30 条窗口满了怎么办 ⭐⭐

**参考答案**
现在就是丢最早的，滑窗。这是最简单也最省 token 的策略，但确实会丢信息。

如果要做得更好，有几种思路：

1. **摘要压缩**：把最早的一批消息让模型总结成一段「对话摘要」，替换掉原文，既保留关键信息又省 token。
2. **分层记忆**：短期窗口存原文，长期记忆抽取「用户画像」（比如「他是大三学生，主要焦虑来源是考研」）单独存，每次带上画像。
3. **按重要性保留**：情绪剧烈波动的那些轮次优先保留。

心理疏导场景其实适合第 2 种——用户的核心困扰比具体措辞更重要。

**可能追问**
- 「摘要会不会丢细节？」→ 会，所以摘要要和原文窗口配合，不能只留摘要。

### Q36. 服务重启后，对话记忆还在吗 ⭐⭐⭐

**参考答案**
**不在。** 这是项目当前的真实缺陷。

`MessageWindowChatMemory` 是进程内的 `ConcurrentHashMap`，没有持久化，重启即清空。而且多实例部署时，请求打到另一台机器，那台机器没有这段记忆，模型就「失忆」了。

但注意：**业务消息是持久化的**，都在 `consultation_message` 表里，所以前端刷新页面、重新点开会话，历史消息还能显示出来——只是模型侧的记忆没了，接着聊它会不记得前面说过什么。

正确做法是把记忆也持久化：要么用 Spring AI 的 Redis 实现（`RedisChatMemory`），要么自己写一个基于 `consultation_message` 表的 `ChatMemory` 实现，按 `conversationId` 查最近 30 条。后者更彻底，一份数据两处用。

**可能追问**
- 「那现在用户重新进入旧会话会怎样？」→ 界面能看到历史，但模型不知道，等于「重新认识」。所以严格说这个功能是半成品。

### Q37. 为什么同一句话不会被存两次 ⭐⭐⭐（体现你考虑过边界）

**参考答案**
因为建会话和发消息是两个接口，同一句初始消息会被传两次：`session/start` 里存一次，`stream` 里又传一次。

我做了个幂等判定，三个条件同时满足才认为「已存过」：

```java
if (messageCount == 1
    && lastMessage.getSenderType() == 1
    && userMessage.equals(lastMessage.getContent())) {
    isInitialMessage = true;   // 跳过入库
}
```

- 消息总数是 1：说明这是会话的第一条；
- 发送方是用户（1）：排除 AI 消息；
- 内容完全一致：确认是同一句话。

三个都成立才跳过。

**但这只覆盖了「初始消息」这一种场景。** 如果用户在网络重试时对 `stream` 重复提交同一句话，还是会重复入库——因为没有基于 `requestId` 的幂等键。更严谨的做法是前端生成一个 `clientMessageId`，后端用唯一索引兜底。

**可能追问**
- 「为什么不用数据库唯一索引？」→ 内容可能合法重复（用户真的连发两次「嗯」），不能按内容做唯一。应该用客户端消息 ID。

### Q38. 用户中途关掉页面，AI 的回复会存下来吗 ⭐⭐⭐（高频陷阱）

**参考答案**
**不会。** 这是我项目里明确的一个缺陷。

因为落库写在 `doOnComplete` 里，只有流正常结束才触发。用户 abort、网络断开、服务重启，都不会走 `doOnComplete`，这条 AI 回复就丢了——但用户那条消息已经存了，所以历史记录里会出现「有问无答」。

而且更浪费的是：客户端断开后，后端**感知不到**（没写 `doOnCancel` / `sink.onDispose`），模型调用会继续跑完，token 照样烧钱。

改进方案：
1. 流开始时就插入一条占位消息（内容为空或 `"..."`），`doOnNext` 里定期更新内容，`doFinally` 里收尾——这样中断也留得下部分内容。
2. 加 `doOnCancel`，客户端断开就取消上游订阅（`Disposable.dispose()`），省 token。

**可能追问**
- 「定期更新会不会写库太频繁？」→ 可以按累计字符数或时间节流，比如每 200 字或每 2 秒更新一次。

### Q39. 你的 Prompt 是怎么设计的 ⭐⭐

**参考答案**
系统提示词单独放在 `PromptManage` 常量类里，分六块：

1. **角色设定**：专业、温暖、有同理心的心理健康助手，服务对象是大学生。
2. **角色特点**：温暖友善、专业不冷漠、善于倾听不急于建议、鼓励积极但不忽视负面情绪。
3. **对话原则**：先共情 → 帮梳理情绪 → 给温和建议 → 必要时鼓励求助 → 强调用户价值。
4. **安全边界**：检测到自杀倾向优先表达关心并引导求助；严重问题建议联系学校心理咨询中心；避免空洞安慰。
5. **回复要求**：贴近大学生、长度适中、可适当用表情、结合校园场景。
6. **语言约束**：全程简体中文。

设计思路是「先定人格，再定流程，最后定红线」。心理场景里第 4 块最重要——它不是让 AI 更聪明，是防止它造成伤害。

**可能追问**
- 「为什么放常量不放数据库？」→ 当前是单人项目，常量最简单；但更好的做法是外置，支持热更新和 A/B 测试，不用改代码重新发版。

### Q40. 怎么防止 AI 输出不当内容 ⭐⭐⭐

**参考答案**
诚实地讲，**目前只有 Prompt 层的软约束，没有硬性拦截**，这是不够的。

现状：Prompt 里写了「检测到自杀倾向要优先共情并引导求助」「严重问题建议联系学校心理咨询中心」。但模型是否遵守，取决于它的理解，不可控。

要做的加固，按优先级：
1. **输入侧关键词检测**：命中自杀/自伤词表时，不走普通对话，直接返回预设的危机干预话术 + 心理援助热线（如 12356），并记录告警。
2. **输出侧过滤**：对模型输出做敏感词/正则扫描，命中则替换或拦截。
3. **兜底话术**：无论模型说什么，界面上常驻「如有紧急情况请联系…」的提示条。
4. **审计**：把高风险对话标记出来，供人工复核（心理场景涉及伦理，必须有）。

这套是「规则兜底 + 模型为主」，不能只靠模型自觉。

**可能追问**
- 「关键词误判怎么办？」→ 分级：轻度命中只提示，重度命中才转人工话术；同时保留上下文判断，避免「我今天心情差到想死」这种夸张表达被误判为危机。

### Q41. 模型调用超时或者报错怎么处理 ⭐⭐

**参考答案**
现在是 `doOnError(sink::error)`，把错误传给前端，前端 `onerror` 里提示「AI 回复失败，请重试」。

不足有三点：
1. **没有超时控制**：`WebClient` 有默认超时，但我没显式配，模型卡住时行为不确定。应该配 `responseTimeout`，比如 60 秒。
2. **没有重试**：网络抖动导致的失败直接暴露给用户。可以对 5xx / 超时做有限重试（比如 2 次，指数退避），但要注意**流式已经开始输出后不能重试**，否则前端会收到重复内容。
3. **没有降级**：模型全挂时应该给一个兜底话术，而不是干巴巴的「失败」。

**可能追问**
- 「流到一半失败了怎么补？」→ 前端保留已收到的内容并标注「（回复中断）」，同时提供「继续生成」按钮；后端把已生成的部分落库。

### Q42. 换一个模型要改多少代码 ⭐

**参考答案**
基本不用改代码，改配置就行。

因为用的是 OpenAI 兼容协议，只要目标厂商支持（DeepSeek、通义、Kimi、硅基流动上的各种模型都支持），改 `application.yml` 里的 `base-url`、`api-key`、`model` 三个值即可：

```yaml
spring.ai.openai.base-url: https://api.siliconflow.cn
spring.ai.openai.chat.options.model: deepseek-ai/DeepSeek-V3
```

业务代码里只依赖 `ChatClient` 接口，不依赖具体实现。

如果要换成非 OpenAI 协议的（比如某些私有部署），才需要换 starter 或者自己实现 `ChatModel` 接口。

**可能追问**
- 「那模型能力差异怎么适配？」→ Prompt 要针对模型调，比如有的模型指令跟随好、有的需要更强的格式约束。这部分是配置 + Prompt 层的事，不是代码结构的事。

## E. 数据库与业务

### Q43. 三张表是什么关系 ⭐

**参考答案**
`user` 一对多 `consultation_session`，`consultation_session` 一对多 `consultation_message`。

- `user`：账号信息，`user_type` 区分普通用户(1)/管理员(2)，`status` 区分正常(1)/禁用(0)，密码存 BCrypt 密文。
- `consultation_session`：会话的「壳」，存标题、开始时间、最后一次情绪分析结果。
- `consultation_message`：消息流水，`sender_type` 区分用户(1)和 AI(2)，`ai_model` 记录用的模型。

一个用户可以开多个会话，一个会话有多条消息。

**可能追问**
- 「为什么要 `sender_type` 而不是两张表？」→ 用户消息和 AI 消息结构完全一样（都是文本 + 时间），拆两张表查询要 union，反而麻烦。用一个字段区分更自然。

---

### Q44. 为什么会话和消息要分表 ⭐⭐

**参考答案**
主要是查询效率和数据量考虑。

会话列表页只需要会话的元信息（标题、时间、条数），如果消息也塞在会话表里，要么用 JSON 字段存数组（无法索引、无法分页），要么每次查会话都带出几千条消息。

分表后：查列表只扫会话表（数据量小），查某个会话的消息按 `session_id` 走索引，两边都快。这也符合一对多关系的标准建模。

**可能追问**
- 「那列表页要显示最后一条消息预览怎么办？」→ 两种做法：冗余一个 `last_message` 字段（更新消息时同步），或者子查询取最新一条。项目里前端有这个字段但后端还没实现，是个待补的点。

---

### Q45. 为什么不用物理外键 ⭐⭐

**参考答案**
三个原因：

1. **写入性能**：每次插消息，数据库都要检查 `session_id` 是否存在，高并发下是额外开销。
2. **分库分表**：将来 `consultation_message` 按 `session_id` 分片，外键跨库根本建不了。
3. **运维灵活**：有外键时删数据顺序被约束，做数据迁移、归档很麻烦。

一致性靠业务层保证：建消息前先确认会话存在（虽然项目里这步也还没做，属于待补）。

**可能追问**
- 「那数据不一致怎么办？」→ 靠事务 + 定期对账脚本。心理数据的核心一致性其实是「消息必须属于存在的会话」，可以用定时任务清理孤儿数据。

---

### Q46. 索引你会怎么建 ⭐⭐

**参考答案**
按查询频率来：

1. `consultation_message` 的 `idx_session (session_id)`——最高频，查某个会话的所有消息。
2. `consultation_session` 的 `idx_user (user_id)`——查某个用户的会话列表。
3. `user` 的 `username`、`email` 唯一索引——登录要按这两个查，且注册时要保证唯一。
4. 如果要按时间倒序取最后一条，`(session_id, created_at)` 联合索引更好，能避免回表排序。

**没必要的**：`status`、`user_type` 这种低基数字段单独建索引意义不大（区分度低，优化器可能不走）。

**可能追问**
- 「联合索引的顺序有讲究吗？」→ 有，遵循最左前缀。`(session_id, created_at)` 能支持「按 session 查 + 按时间排序」，反过来不行。
- 「怎么确认索引生效？」→ `EXPLAIN` 看 `type` 和 `key`，避免 `ALL` 全表扫。

### Q47. 你的项目用事务了吗 ⭐⭐⭐

**参考答案**
**没有，这是个明确的缺陷。**

有两处是多步写操作，应该加 `@Transactional`：

1. **注册**：查用户名是否存在 → 查邮箱是否存在 → 插入用户。极端情况下两个请求并发，都查到「不存在」，然后都插入成功，产生重复账号。加事务 + 数据库唯一索引双保险。
2. **建会话**：查用户 → 插会话 → 插初始消息。如果插消息失败，会话记录会残留一条空会话。

正确做法是 service 方法上加 `@Transactional(rollbackFor = Exception.class)`，注意默认只回滚 `RuntimeException`，检查型异常要显式指定。

**可能追问**
- 「`@Transactional` 什么情况下会失效？」→ 同类内部方法调用（不走代理）、方法不是 public、异常被 catch 没抛出去、非运行时异常没配 `rollbackFor`、多线程里失效。这几个是高频考点。
- 「事务和流式冲突吗？」→ 冲突。流式是长连接，不能把整段流包在一个事务里（事务持有连接太久）。所以落库应该单独开短事务。

### Q48. 分页是怎么做的 ⭐⭐

**参考答案**
**后端目前没做**，这是缺陷。前端页面传了 `pageNum` / `pageSize`，但对应的分页接口在后端不存在。

原因是我没有注册 MyBatis-Plus 的分页插件 `PaginationInnerInterceptor`——没有它，`selectPage` 不会自动拼 `LIMIT`，查出来是全量数据。

如果要补，三步：
1. 配 `MybatisPlusInterceptor` 加 `PaginationInnerInterceptor(DbType.MYSQL)`；
2. Service 里 `mapper.selectPage(new Page<>(pageNum, pageSize), wrapper)`；
3. 返回 `Page` 对象，前端取 `records` 和 `total`。

**可能追问**
- 「深分页怎么优化？」→ `LIMIT 100000, 10` 会扫 10 万行。可以改成「游标分页」（`WHERE id > lastId LIMIT 10`），或者先查主键再回表。

### Q49. 会话 ID 为什么要加 `session_` 前缀 ⭐⭐

**参考答案**
三个作用：

1. **可逆解析**：后端拿 `"session_12"` 能反解出主键 12（`substring` 掉前缀），不用额外查库。
2. **概念隔离**：数据库主键是数字，直接暴露给前端不好；加前缀后前端拿到的是一个「令牌」式的标识，将来换 ID 生成策略（雪花、UUID）不影响前端。
3. **区分 ID 类型**：模型记忆用的是 `"conversation_session_12"`，和业务会话 ID 分开，避免两套系统用同一个字符串产生歧义。

**可能追问**
- 「为什么不直接传数字？」→ 也可以，但那样前后端就耦合在「主键是自增数字」这个实现细节上了。

### Q50. 消息表为什么有 `emotion_tag` 和 `ai_model` 字段 ⭐⭐

**参考答案**
`emotion_tag` 是给情绪分析留的——每条消息可以打一个情绪标签（焦虑、平静等），将来做情绪趋势统计时按标签聚合。现在基本是 null，因为情绪分析接口还没实现。

`ai_model` 记录这条 AI 回复是哪个模型生成的，固定写 `"openai"`（其实底层是 DeepSeek）。作用是**可追溯**——将来多模型灰度、A/B 测试时，能对比不同模型的效果；出问题时也能定位是哪个模型抽风。

**可能追问**
- 「`ai_model` 写 openai 是不是错的？」→ 严格说不准确，应该写 `deepseek-v3` 或 `deepseek-ai/DeepSeek-V3`，因为走的是硅基流动的兼容层。这是命名不严谨，可以改。

### Q51. `user_type` 和 `status` 为什么用数字不用字符串 ⭐

**参考答案**
三个原因：

1. **省空间 + 索引效率**：TINYINT 占 1 字节，字符串至少几个字节，索引也更大。
2. **避免拼写错误**：`"active"` / `"Active"` / `"ACTIVE"` 这种不一致在字符串里很常见，数字不会。
3. **扩展性好**：加新状态只加数字，不用改字段长度。

代价是可读性差，所以配了枚举类 `UserType` / `UserStatus` 做语义映射，代码里用 `UserStatus.NORMAL.getCode()` 而不是裸写 `1`。

**可能追问**
- 「为什么不用数据库 ENUM？」→ MySQL 的 ENUM 改值要 `ALTER TABLE`，而且跨库迁移麻烦，业界更推荐 TINYINT + 应用层枚举。

### Q52. 数据量大了怎么优化 ⭐⭐⭐

**参考答案**
分几个层次：

**索引层**：`session_id`、`user_id` 必须有索引；高频的「取最后一条消息」用 `(session_id, created_at)` 联合索引。

**查询层**：会话列表不要 N+1（每个会话查一次最后消息），改成一次 `GROUP BY` 或子查询；列表字段只 select 需要的列，别 `SELECT *`。

**存储层**：`consultation_message` 是增长最快的表。可以按时间分区（按月），或者冷热分离——3 个月前的内容归档到历史表/对象存储。心理数据合规要求可能还得保留，所以归档比删除更合适。

**缓存层**：会话元信息、用户信息可以进 Redis；情绪分析结果这种计算贵的更适合缓存。

**架构层**：真到千万级，`consultation_message` 按 `session_id` 哈希分片。

**可能追问**
- 「先做哪个？」→ 先 EXPLAIN 找慢查询，别盲目加索引。大多数时候问题在 N+1 和缺索引，不在分库分表。

## F. 前端（后端岗问得不深，但要能答）

### Q53. Vue 3 组合式 API 和选项式有什么区别 ⭐

**参考答案**
选项式是按「类型」组织代码：data 放数据、methods 放方法、computed 放计算属性，一个功能的逻辑被拆到四五个块里。

组合式是按「功能」组织：一个 `setup` 里可以把相关的 `ref`、`computed`、`watch`、方法写在一起，还能抽成 `useXxx()` 复用。Vue 3 的 `<script setup>` 是最简洁的写法，顶层声明的变量自动暴露给模板。

我项目里全部用 `<script setup>`，比如 `consultation.vue` 里会话列表、流式对话、情绪花园三块逻辑是分开的，读起来清楚。

**可能追问**
- 「组合式有什么缺点？」→ 对新手不直观，响应式丢失（解构 `reactive` 对象会失去响应性）这类坑需要经验。

---

### Q54. ref 和 reactive 有什么区别 ⭐

**参考答案**
`ref` 可以包任何类型（基本类型、对象、数组），通过 `.value` 访问，模板里自动解包。

`reactive` 只能包对象/数组，直接访问属性，但**解构会丢失响应性**，而且不能整体替换。

我的用法：单个值（`isAiTyping`、`userMessage`）用 `ref`；表单对象（`diaryForm`、`formData`）用 `reactive`，因为要整块绑定 v-model。

**可能追问**
- 「为什么解构 reactive 会丢响应性？」→ `reactive` 返回的是 Proxy，解构出来的是当时的值，脱离了 Proxy 的 get 拦截。要用 `toRefs` 包一层。

### Q55. 路由懒加载怎么做的 ⭐

**参考答案**
`component: () => import('@/views/dashboard.vue')`，动态 import 返回 Promise，Vite 打包时会把它单独切成一个 chunk，只有访问该路由时才加载。

首屏只加载当前页面的代码，其他页面按需下载。管理端和用户端是完全分开的两套页面，懒加载收益明显。

**可能追问**
- 「首屏还能怎么优化？」→ 路由预加载（`prefetch`）、组件按需引入（Element Plus）、图片压缩、gzip/brotli。

---

### Q56. Axios 拦截器做了什么 ⭐

**参考答案**
请求拦截：从 localStorage 取 token，塞进 `config.headers['token']`，业务代码不用管鉴权。

响应拦截：判断 `code`，`"200"` 就把 `data.data` 剥出来直接返回（调用方拿到的就是业务数据，不用到处 `.data.data`）；`"-1"` 就清 token、清用户信息、跳登录页。

另外统一 `baseURL: '/api'` 和 5 秒超时。

**可能追问**
- 「5 秒超时够吗？」→ 普通接口够，AI 流式不走 axios（走 fetch），所以不影响。但如果将来有导出报表这类慢接口，要单独放宽。

---

### Q57. 前后端返回格式怎么统一的 ⭐⭐

**参考答案**
后端统一 `{ code, msg, data }`，前端在响应拦截器里剥壳。

但这里**有个真实的契约问题**：我后端业务异常的 code 是 `"BUSINESS_ERROR"`，前端只处理了 `"200"` 和 `"-1"`。结果就是登录失败时，前端拿到的既不是成功也不是失效，而是原样的 response 对象，`data.token` 是 undefined，页面表现为「点登录没反应」。

根因是错误码没有统一设计——早期用了 `"200"/"-1"`，后来业务异常又单独起了个 `"BUSINESS_ERROR"`，前端没跟上。

正确做法是定一套错误码枚举，前端集中处理：成功一个码、认证失效一类码、业务错误一类码，业务错误统一 toast `msg`。

**可能追问**
- 「那你怎么发现的？」→ 注册页面有个解构 bug（`.then(({ data }) => ...)`，但拦截器已经剥壳了，`data` 是 undefined），导致注册失败也提示成功。两个问题叠加才暴露出来。

### Q58. Pinia 用在哪里 ⭐

### Q59. ECharts 怎么集成的 ⭐

**参考答案**
`import * as echarts from 'echarts'`，在 `onMounted` 里 `echarts.init(domRef.value)`，然后 `setOption(option)`。

项目里有三张图：情绪趋势（折线）、咨询量统计（柱状 + 渐变色 `LinearGradient`）、用户活跃度（多条折线）。数据来自 `/api/data-analytics/overview`，拿到后先赋值再 `initCharts()`。

**要主动说的一个缺陷**：没做窗口 resize 监听，浏览器窗口变化时图表不会自适应。正确做法是 `window.addEventListener('resize', () => chart.resize())`，并且在 `onUnmounted` 里移除监听 + `dispose()`，否则内存泄漏。

**可能追问**

### Q60. 富文本编辑器怎么用的 ⭐⭐

## G. 工程化与开放题

### Q61. 统一返回结构是怎么设计的 ⭐

**参考答案**
`Result<T>` 三个字段：`code`（String）、`msg`、`data`（泛型）。提供 `ok()`、`ok(data)`、`error()`、`error(code,msg,data)` 四个静态工厂。

`code` 用 String 而不是 int，因为错误码里有 `"A0230"` 这种带字母的（借鉴了 Sa-Token 的风格）。

**可能追问**
- 「code 用 String 有什么坏处？」→ 前端比较要注意类型（`"200" !== 200`），而且没法做区间判断（比如 4xx 统一处理）。int 其实更好，项目里这里是个可以商量的设计。

---

### Q62. 参数校验怎么做的 ⭐

**参考答案**
两层。

第一层 DTO 注解：`@NotBlank`、`@Size`、`@Email`、`@Pattern`，Controller 参数加 `@Valid`。

第二层业务校验：Service 里查库判断（用户名是否已存在、密码是否一致），抛 `BusinessException`。

第一层失败抛 `MethodArgumentNotValidException`，被 `@RestControllerAdvice` 捕获，把所有字段错误消息拼成一句话返回。

**可能追问**
- 「分组校验怎么做？」→ `@Validated` + 分组接口（`Create.class`、`Update.class`），同一个 DTO 在不同场景校验不同字段。
- 「自定义校验注解？」→ 实现 `ConstraintValidator`，比如「手机号必须是中国大陆号码」。

---

### Q63. 全局异常处理怎么做的 ⭐⭐

**参考答案**
`@RestControllerAdvice` + `@ExceptionHandler`，我处理了两类：

1. `MethodArgumentNotValidException`：提取所有 `FieldError.getDefaultMessage()`，用 `", "` 拼接返回。
2. `BusinessException`：返回它自己的 code 和 message。

**不足**：没有兜底 `Exception` 处理器。未捕获的异常（NPE、SQL 异常）会走 Spring 默认错误页，返回 `{timestamp, status, error, path}` 这种结构，和我的 `Result` 不一致，前端解析会出错。

应该加一个 `@ExceptionHandler(Exception.class)` 兜底，统一返回 `code=500`，同时打 error 日志（带 traceId）。

**可能追问**
- 「`@RestControllerAdvice` 和 `@ControllerAdvice` 区别？」→ 前者相当于后者 + `@ResponseBody`，直接返回 JSON。

---

### Q64. 跨域怎么解决的 ⭐⭐

**参考答案**
开发期靠 Vite 代理：前端请求 `/api/**`，Vite dev server 转发到后端 `localhost:1236`，浏览器看来是同源，没有跨域。

生产环境两种方案：Nginx 把前后端放在同一个域名下（`/api` 反代到后端），或者后端加 CORS 配置（`CorsConfigurationSource` 允许指定 origin）。项目里没写 CORS 配置，因为开发靠代理，上线还没做。

**注意**：如果用 CORS，`allowCredentials(true)` 时 `allowedOrigins` 不能是 `*`，必须指定具体域名。

**可能追问**
- 「预检请求是什么？」→ 非简单请求（自定义头、PUT/DELETE、JSON Content-Type）会先发 `OPTIONS`，后端要允许 `OPTIONS` 并返回正确的 `Access-Control-Allow-*` 头。

### Q65. 项目怎么部署 ⭐⭐

**参考答案**
**目前是手工部署，没有 CI/CD**，这是短板。

我设想的正常流程：前端 `npm run build` 出静态文件，扔给 Nginx；后端 `mvn package` 出 jar，`java -jar` 跑（或者打成 Docker 镜像）；Nginx 把 `/api` 反代到后端端口，同时给前端做 history 模式的 fallback（`try_files $uri $uri/ /index.html`）。

要注意两个点：SSE 必须关掉 Nginx 缓冲（`proxy_buffering off`），否则流式失效；`proxy_read_timeout` 要调大，不然长连接会被掐断。

**可能追问**
- 「Docker 怎么打？」→ 后端用多阶段构建（maven 镜像编译 + jre 镜像运行），前端 build 后拷进 nginx 镜像。

### Q66. 日志是怎么打的 ⭐

**参考答案**
**坦白说，是 `System.out.println`，不规范。**

代码里有多处 `System.out.println`（过滤器里打 URI、UserService 里打用户对象和 token、会话服务里打参数）。问题是：没有级别、没有时间戳、没法按级别过滤、生产环境可能拖慢性能，而且**打印了 token**，是安全问题。

正确做法是 SLF4J + Logback：`log.info("用户登录成功, userId={}", userId)`，用占位符而不是字符串拼接；敏感信息脱敏；配 rolling file 和 JSON 格式方便采集。

**可能追问**
- 「为什么不能字符串拼接？」→ 占位符在日志级别不满足时不会执行拼接，省性能；而且能避免敏感信息被无意拼进日志。

### Q67. 有没有写单元测试 ⭐

### Q68. 开发过程中遇到最难调的 bug 是什么 ⭐⭐

**参考答案**
（用真实经历，这里给一个可用的素材）

流式对话写完，前端一直收不到完整回复，就卡在那里不结束。排查过程：

先看后端日志，模型确实在返回片段；再看网络面板，响应是 200 且 Content-Type 正确，但流一直不结束。最后发现是 `sink.complete()` 没被调用——因为我在 `doOnComplete` 里先写了数据库，而写库抛了异常（字段超长），异常把 `complete` 之前的逻辑打断了，流就永远不结束。

修法是 `doOnComplete` 里把落库包 try-catch，落库失败也要 `sink.complete()`；同时在 `doOnError` 里补 `sink.error()`。

这个 bug 让我理解了一件事：**响应式流里，终止信号（complete/error）必须保证被调用，否则下游永远挂着**。

**可能追问**
- 「怎么快速定位这类问题？」→ 在流的关键节点加 `doOnSubscribe` / `doOnNext` / `doOnComplete` / `doOnError` / `doOnCancel` 打点，看信号走到哪一步断了。

### Q69. 你觉得这个项目有什么不足 ⭐⭐（几乎必问）

**参考答案**
我分三类说。

**可靠性上的**：流式回复只在 `doOnComplete` 落库，用户中途关页面就丢；记忆是内存实现，重启和多实例都会失忆；没有超时和重试。

**安全上的**：JWT 没有 refresh 和黑名单，24 小时有效期偏长；后端没做角色级鉴权，只有前端路由守卫；Prompt 只有软约束，没有关键词硬拦截；日志里打印了 token。

**工程上的**：没加 `@Transactional`；没有单元测试；配置里明文放密钥；Element Plus 全量引入。

这些问题我知道怎么改，比如记忆改成基于 `consultation_message` 表的自定义 `ChatMemory` 实现，一份数据两处用；流式改成先落占位再增量更新；鉴权加 `@PreAuthorize`。

**⚠️ 关键**：说不足时一定要带方案，否则听起来像「做完了但质量差」；带方案才是「知道边界在哪」。

### Q70. 如果用户量涨到十万，你会怎么改 ⭐⭐⭐

**参考答案**
先看瓶颈在哪，不要盲目上架构。按顺序：

**第一步，压测找瓶颈**。十万用户不等于十万并发，先算 QPS。这个产品的瓶颈大概率在两个地方：AI 调用（慢、贵、有 RPM 限制）和 SSE 长连接（占线程/连接）。

**第二步，针对 AI**：
- 加请求队列 + 限流（每用户每分钟 N 次），避免被打爆配额；
- 相同问题做语义缓存（相似问法命中缓存直接返回，省 token）；
- 记忆搬到 Redis，支持多实例；
- 模型调用加熔断降级（Resilience4j）。

**第三步，针对连接**：
- SSE 长连接会占 Tomcat 线程吗？异步 Servlet 不会一直占线程，但连接数上去了要调 Tomcat 的 `maxConnections`；
- 多实例部署 + Nginx 负载均衡，注意 SSE 需要 `proxy_read_timeout` 调大、关缓冲；
- 如果单机连接数顶不住，考虑把 AI 网关独立成一个服务。

**第四步，数据层**：
- 消息表按月分区或冷热分离；
- 热点数据（用户信息、会话元信息）进 Redis；
- 读写分离，心理场景读多写少，适合。

**第五步，可观测性**：链路追踪（traceId 贯穿前后端 + AI 调用）、AI 调用的耗时/成功率/token 消耗监控。没有监控的优化都是猜。

**可能追问**
- 「为什么不一上来就微服务？」→ 十万用户、单体 + 多实例大概率扛得住。微服务的运维成本和分布式事务复杂度，在这个阶段是负收益。
